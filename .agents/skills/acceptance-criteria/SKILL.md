# 인수 조건 작성

요구사항을 구현 방식이 아니라 외부에서 관찰 가능한 행동과 결과로 바꾼다. 각 조건은 한 가지 판단만 포함하고 참·거짓으로 판정할 수 있어야 한다.

## 참조

- `../../../references/planning-principles.md`
- `../../../references/service-context.md`
- `../../../references/glossary.md`
- 관련 사용자 흐름, 정책 정의서, 화면 정의서를 읽는다.

## 작성 절차

1. 검증할 사용자 목표와 범위를 정한다.
2. 정상 흐름의 시작 조건, 행동, 기대 결과를 작성한다.
3. 입력 경계값, 권한, 상태, 중복 행동, 실패·복구 조건을 추가한다.
4. 각 조건을 관련 흐름·정책·화면 요소와 연결한다.
5. 정책이 미정이라 기대 결과를 정할 수 없으면 AC를 만들지 않고 `결정 필요`로 남긴다.

## 출력 형식

```markdown
# {기능명} 인수 조건

## 1. 범위

| 항목 | 내용 |
| --- | --- |
| 사용자 목표 | ... |
| 관련 문서 | F-01, POL-01, SCR-01 |
| 검증 제외 범위 | ... |

## 2. 유저 스토리

{사용자 역할}로서, {목표}를 위해 {행동/기능}을 원한다.

## 3. 인수 조건

### AC-01 {판정 가능한 제목}

- Given: {시작 상태와 선행 조건}
- When: {사용자의 행동 또는 사건}
- Then: {관찰 가능한 결과}
- 관련 항목: {F-01-01, POL-01, SCR-01-E01}

## 4. 경계·예외 조건

| AC ID | 구분 | 조건 | 기대 결과 | 관련 정책·화면 |
| --- | --- | --- | --- | --- |
| AC-02 | 입력 경계/권한/실패/복구 | ... | ... | ... |

## 5. 결정 필요

- [ ] {기대 결과를 확정하려면 필요한 정책} — 영향 AC: {AC-...}
```

## 작성 원칙

- `정상적으로 처리된다`, `적절한 메시지`처럼 검증할 수 없는 결과를 쓰지 않는다.
- 내부 함수명, 데이터베이스 구조 등 사용자가 요구하지 않은 구현 방법을 인수 조건으로 고정하지 않는다.
- 하나의 AC에 여러 독립 행동이 섞이면 나눈다.
- 같은 행동이라도 사용자 역할이나 시작 상태가 다르면 별도 조건으로 작성한다.
- 시간·성능 기준은 근거가 있을 때만 수치화하고, 없으면 결정 필요로 남긴다.

## 완료 기준

- 정상·제한·실패·복구 중 기능과 관련된 조건이 포함된다.
- 각 AC는 단독으로 실행하고 판정할 수 있다.
- 모든 기대 결과가 확정된 정책 또는 명시된 가정에 근거한다.
