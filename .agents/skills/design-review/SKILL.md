# 제품 디자인 정합성 검토

작성자와 독립된 관점에서 제품 의도가 시스템과 실제 UI까지 일관되게 이어지는지 확인한다.

## 참조

- `../../../references/planning-principles.md`
- `../../../references/design-principles.md`
- `../../../references/product-design-handoff.md`
- 사용자가 지정한 실제 `planning/`, `design/` 산출물

## 검토 기준

### 추적성

- UI가 제품 목표, 흐름, 정책과 연결되는가?
- 컴포넌트와 토큰이 디자인 원칙 및 실제 사용처와 연결되는가?
- 개발 인계가 관련 UI, COPY, AC와 EVT를 참조하는가?
- 시각 UI를 제작했다면 `visual-index.md`의 파일·노드가 UI 명세와 연결되고 다시 열 수 있는가?

### 시스템 일관성

- 화면이 임의 값이나 비공식 공통 컴포넌트를 만들지 않았는가?
- 같은 용어, 상태와 컴포넌트가 문서마다 같은 뜻인가?
- `GAP-*`의 판정과 반영 상태가 추적되는가?

### 경험 완전성

- 정상, 로딩, 빈 상태, 오류, 권한, 취소와 복구를 필요한 만큼 다루는가?
- UI, 문구와 접근성 요구가 같은 사용자 결과를 설명하는가?
- 반응형과 긴 콘텐츠에서 핵심 행동이 유지되는가?

## 심각도

| 등급 | 기준 |
| --- | --- |
| Blocker | 제품 결과나 시스템 방향이 갈려 결정 없이는 진행 불가 |
| Major | 사용 실패, 접근성 문제, 시스템 파편화 또는 구현 불가 가능성이 큼 |
| Minor | 구현 가능하지만 해석 차이나 유지보수 비용이 발생 |
| Question | 문서만으로 판단할 수 없어 결정이나 근거 확인 필요 |

## 출력 형식

```markdown
# 제품 디자인 정합성 검토 보고서

## 결론
- 진행 가능 여부:
- Blocker / Major:
- 검토하지 못한 범위:
- 시각·실사용 검증 여부:

## 발견 사항
### DREV-{NN} [{심각도}] {제목}
- 근거:
- 현재 내용:
- 문제와 사용자 영향:
- 필요한 조치:
- 영향 ID:

## 추적성 누락
## 시스템 공백 상태
## 결정 질문
## 확인 완료
```

## 작업 원칙

- 원문을 직접 수정하지 않는다.
- 근거 위치가 없는 일반적인 조언은 발견으로 등록하지 않는다.
- 같은 원인의 문제는 하나로 묶고 전체 영향 범위를 연결한다.
- 이전 보고서가 있으면 해결됨, 미해결, 새로 발생을 구분한다.
