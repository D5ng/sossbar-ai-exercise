# 서비스 기획 오케스트레이터

기획서 → IA → 유저 플로우 → 화면 요구사항 정의서 순서로 작성한다. 사용자가 필요한 단계만 요청하면 그 범위만 실행하고, 앞 단계 정보가 부족한 부분은 가정과 결정 필요로 표시한다.

## 구성

| 단계 | 스킬 | 일반 명칭 | 기본 출력 |
| --- | --- | --- | --- |
| 0 | 공통 컨텍스트 | - | `planning/00-service-context.md`, `planning/00-glossary.md` |
| 1 | `product-brief` | 서비스 기획서 | `planning/01-product-brief.md` |
| 2 | `information-architecture` | IA·사이트맵 | `planning/02-information-architecture.md` |
| 3 | `user-flow` | 유저 플로우 | `planning/03-user-flow.md` |
| 4 | `screen-spec` | 화면 요구사항 정의서 | `planning/04-screen-specs/{screen-id}.md` |

```text
00 공통 컨텍스트 ─ 원칙 · 공통 점검 목록 · 용어 사전 · 기존 산출물 확인
│
▼
01 서비스 기획서 ─ MVP 범위 · 공통 점검 판정
│
▼
02 IA ─ 화면 ID(SCR) · 접근 제어 부여   ◀┐
│                                        │
▼                                        │
03 유저 플로우 ─ IA에 없는 화면은 '신규' ─┘
│
▼
04 화면 요구사항 정의서 ─ 요소 · 상태 · 화면 규칙(SCR-*-R*)
│
▼
완료 보고 → 요청 시 디자인 인계 점검
```

- 정책서는 따로 만들지 않는다. 권한은 IA 접근 제어에, 입력·상태·저장·삭제·알림 규칙은 화면 정의서의 `화면 규칙`에 둔다. 여러 화면에 걸치는 규칙은 처음 적용되는 화면에 두고 다른 화면은 그 ID를 참조한다.
- 와이어프레임과 배치는 디자인 단계의 `product-ui-design`이 맡는다.
- 사용자가 출력 루트를 지정하면 `planning/` 앞에 그 경로를 붙인다. 새 서비스나 실험 산출물은 기존 결과를 덮어쓰지 않는다.
- 이전 구조(정책서·인수 조건·트래킹 플랜·`05-screen-specs/`가 있는 구성)로 만든 산출물이 있으면 파일명과 경로를 바꾸지 않고 그대로 이어서 쓴다.

## 절차

1. `../../../references/planning-principles.md`, `../../../references/web-service-checklist.md`를 읽고, 기존 `planning/` 산출물과 사용자 자료를 확인한다. `00-glossary.md`가 없으면 `references/glossary.md` 양식으로 만든다.
2. 이번 범위를 정한다: 서비스 전체인지 특정 기능인지, 필요한 문서, 판정할 공통 점검 영역. 선택에 따라 핵심 범위가 크게 달라질 때만 먼저 질문한다.
3. 단계 순서대로 해당 스킬(`../product-brief/SKILL.md`, `../information-architecture/SKILL.md`, `../user-flow/SKILL.md`, `../screen-spec/SKILL.md`)을 읽고 작성한다.
   - 상위 문서의 식별자를 유지하고, 충돌하면 하위 문서에서 임의로 해결하지 않고 결정 필요로 올린다.
   - 흐름에서 `신규` 화면이 생기면 흐름을 마친 뒤 IA에 추가하고 화면 정의서로 넘어간다.
   - 새 용어·역할·상태 이름은 `00-glossary.md`에 추가한다.
4. 확정된 결정은 사용자 요청 없이 바꾸지 않는다.

리서치로 가정(`AS-*`)이나 설계를 검증하고 싶으면 `user-interview` 스킬(`skills/research/user-interview/SKILL.md`), `usability-test` 스킬(`skills/research/usability-test/SKILL.md`)을 제안할 수 있다. 반영 제안은 사용자가 채택한 것만 반영한다.

## 부분 재실행

| 변경 문서 | 다시 확인할 문서 |
| --- | --- |
| 서비스 기획서 | IA, 흐름, 화면 |
| IA | 흐름의 화면 ID, 화면 진입·접근 조건 |
| 유저 플로우 | IA(신규 화면), 화면 |
| 화면 요구사항 정의서 | 규칙을 참조하는 다른 화면 |

내용이 여전히 유효하면 다시 쓰지 않는다.

## 디자인 인계

디자인 요청이 이어지면 `../../../references/product-design-handoff.md`의 `디자인 인계 점검`을 판정한다. `DHC-01`~`DHC-08`은 기획 문서로 확인하고, `DHC-09`~`DHC-13`은 사용자에게 한 번에 묻는다. 답이 없어도 멈추지 않고 `없음`으로 넘기며, 브랜드 값이나 샘플 데이터를 대신 만들지 않는다.
