# 소스바(Sossbar) 서비스 기획서

> 팀의 경험을 회고하고 동료에게 피드백을 남겨, 내가 어떻게 일하는 사람인지 프로필에 쌓는 서비스입니다.

작성일: 2026-10-05

최종 수정일: 2026-10-06

이 문서는 현재 제품 기획입니다. 실제 화면 배치와 개발 방법은 후속 설계에서 구체화합니다.

**처음 읽는 분은 1~8장을 먼저 읽으면 됩니다.** 서비스 소개, 용어, 작성 위치, 이용 순서와 공개 범위를 설명합니다. 9~14장은 검증 계획·출시 준비·기획 관리용 참고 자료입니다.

문서의 **확정**은 제품 방향을 정했다는 뜻이고, **결정 필요**는 세부 규칙이 남아 있다는 뜻입니다. **검증 필요**는 사용자가 실제로 가치를 느끼는지 아직 확인하지 않았다는 뜻입니다. 정한 방향과 검증된 효과는 구분합니다.

`DEC-24` 같은 표시는 ‘24번 제품 결정’이라는 관리번호입니다. 서비스 기능이나 사용자가 외워야 할 용어가 아닙니다. 본문에서는 번호를 줄였고, 뜻과 연결 자료는 12장에 모았습니다.

## 1. 한눈에 보기

소스바의 핵심 경험은 **프로젝트 참여 → KPT 작성 → 선택적으로 동료 피드백 → 프로필에 기록 쌓기**입니다.

팀은 매주·매월 등 회고 주기를 정합니다. 방장이 그 주기에 맞춰 1차·2차·3차 회고를 만들면, 팀원들이 이번 협업을 돌아보고 다음에 바꿀 행동을 정합니다. 각자는 KPT를 제출한 뒤 원하는 동료에게 피드백을 남길 수 있습니다.

| 활동 | 사용자에게 남는 것 |
| --- | --- |
| 팀 회고 | 팀이 유지할 방식, 겪은 문제, 다음에 시도할 행동 |
| 동료 피드백 | 특정 동료가 어떻게 일했는지, 어떤 순간에 도움이 됐는지에 대한 기록 |
| 개인 프로필 | 직무·프로젝트 경험과 본인이 선택해 공개한 동료 기록 |

**KPT를 썼다고 동료가 본 나의 기록이 자동으로 생기지는 않습니다.** 누군가 나에게 동료 피드백을 남겨야 그 기록이 생깁니다. 동료 기록이 없을 때에는 프로젝트 기본 정보·선택적인 역할·자기 스타일을 보여줄 수 있지만, 초기 프로필 내용은 적을 수 있습니다.

처음에는 부트캠프·교육과정의 팀 프로젝트 참가자를 우선 대상으로 합니다. 카카오 로그인 한 종류로 시작하고 PC·모바일 웹을 지원합니다. 공개 프로필은 로그인 없이 읽을 수 있습니다.

## 2. 누구를 위한 서비스인가요?

협업 중 드러난 기여와 일하는 방식을 다음 프로젝트에 가져갈 기록으로 남기기 어렵다는 문제에서 출발했습니다. 동료에게 별도로 후기를 부탁하는 부담을 줄이고, 내 생각과 동료의 관찰을 함께 확인하려는 서비스입니다. 이 불편이 얼마나 크고 실제로 사용하고 싶은지는 검증해야 합니다.

| 사용자 | 소스바에서 하려는 일 |
| --- | --- |
| 프로젝트 참가자 | 팀 경험을 회고하고, 동료 피드백을 주고받으며, 협업 기록을 남김 |
| 미래의 협업 상대 | 공개된 프로필을 읽고 그 사람이 어떻게 일했는지 이해 |
| 교육기관 담당자 | 팀의 회고 진행을 지원하고 팀 단위 참여 상태 확인 |

첫 출시는 참가자의 회고·피드백 작성과 프로필 형성에 집중합니다. 팀원 검색·매칭이나 교육기관의 여러 팀을 관리하는 화면은 후속입니다.

## 3. 서비스에서 이루려는 것

- 프로젝트 맥락과 동료의 구체적인 관찰을 개인 프로필에 남깁니다.
- 팀이 다음 협업에서 시도할 행동을 정하도록 돕습니다.
- 자기 스타일과 동료가 관찰한 스타일을 구분해 확인하도록 합니다.
- 회고와 연결한 요청이 실제 피드백 작성·프로필 공유로 이어지는지 확인합니다.

사람의 협업 능력·신뢰도를 점수나 등급으로 판정하지 않습니다. 프로젝트 참여나 링크만으로 실제 기여를 인증하지 않으며, 비공개 내용을 수료 판정·개인 평가 자료로 제공하지 않습니다. 피드백 전원 작성·최소 인원 작성을 팀이 강제하는 옵션은 첫 출시에서 제외합니다.

## 4. 용어와 작성 위치

### 4.1 프로젝트 참여와 기본 정보

**프로젝트**는 팀의 협업 경험과 여러 회고를 담는 공간입니다. 한 사람이 이름·기간·팀 규모·목표와 결과·프로젝트 공통 산출물 링크를 등록하고 팀원을 초대합니다. 이 사람이 최초 방장이며, 다른 구성원에게 방장 역할을 넘길 수 있습니다.

팀원은 카카오로 로그인해 초대를 수락합니다. 등록된 프로젝트 이름·기간은 프로필에 연결하므로 각자가 다시 작성하지 않습니다. ‘내 역할’은 프로젝트 참여 후 기본 정보에서 짧게 선택 입력할 수 있고 나중에도 수정할 수 있습니다.

| 정보 | 뜻과 예시 | 작성 위치 |
| --- | --- | --- |
| 직무 | BE(백엔드 개발)·FE(프론트엔드 개발)·PM(프로덕트 매니저)·PD(프로덕트 디자이너) 등 | 프로필 기본 정보 |
| 프로젝트 역할 | 해당 프로젝트에서 맡은 역할의 짧은 설명. 예: ‘프론트엔드 개발’ | 프로젝트 기본 정보의 ‘내 역할’ 선택 항목 |
| 프로젝트 공통 정보 | 프로젝트 이름·기간·목표·공통 산출물 링크 등 | 등록자가 프로젝트를 만들 때 작성 |

프로필 직무와 프로젝트 역할은 구분합니다. 직무나 역할 입력이 팀원 자격·방장 권한 또는 실제 역량의 인증을 뜻하지 않습니다. 직무의 필수 여부·단일/복수 선택·기타 항목은 아직 정하지 않았습니다.

**별도의 ‘내 프로젝트 기록’ 작성 단계는 첫 출시에 없습니다.** 상세 기여·개인 산출물 서술은 후속입니다. 프로젝트별 역할은 매 회고마다 다시 쓰지 않으며, 역할을 입력하지 않아도 KPT와 동료 피드백을 이용할 수 있습니다.

### 4.2 회고 주기·차수와 KPT

**회고 주기**는 팀이 얼마나 자주 회고할지 정한 간격입니다. 매주·매월은 예시이며 서비스가 고정하지 않습니다. **회고 차수**는 그 프로젝트에서 진행하는 한 번의 회고입니다. 1차·2차·3차마다 작성 기간·마감·기록·완료 상태를 따로 관리합니다.

**KPT**는 팀의 경험을 세 가지로 나누어 돌아보는 방식입니다.

| 항목 | 묻는 내용 | 예시 — 설명용 |
| --- | --- | --- |
| Keep: 유지할 것 | 어떤 행동이 어떤 도움을 줬나? | 중간 진행 공유가 막힌 일을 발견하는 데 도움이 됐다 |
| Problem: 겪은 문제 | 어떤 상황에서 어떤 불편이 생겼나? | 기획 변경이 늦게 공유돼 재작업이 생겼다 |
| Try: 다음에 시도할 것 | 다음에 무엇을 바꿔볼까? | 기획 변경은 당일 공유 채널에 남겨보자 |

개인 KPT 입력 화면에 위와 같은 쉬운 질문과 예시를 제공합니다. 숫자·원인 분석을 필수로 요구하지 않고 구체적인 상황·행동을 적도록 돕습니다. 원인을 적을 때는 확인한 사실과 추측을 구분하며, 사람에 대한 평가보다 상황·작업 방식에 집중하도록 안내합니다.

방장은 차수를 직접 만들고 회고 대상 기간·KPT 마감·동료 피드백 마감을 설정합니다. 작성 요청을 시작하면 해당 차수 참가자 전원에게 KPT 작성을 요청합니다. 전원 제출까지 진행을 막지는 않습니다.

마감 후에는 제출된 원문을 K·P·T별로 모아 작성자 이름·참여 및 제출 인원과 함께 팀에 보여줍니다. AI 요약이나 자동 결론으로 대체하지 않습니다. 팀이 논의해 실제 실행할 Try를 선택하고 방장이 차수를 완료합니다. 팀의 실행 항목은 개인이 제안한 Try와 구분해 저장합니다.

**팀이 선택한 Try는 실행 항목별로 한 문장으로 남깁니다.** ‘누가 언제 무엇을 할지’를 예시로 안내하며 담당자·기한을 별도 입력칸으로 만들거나 각각 필수로 요구하지 않습니다. 예: ‘FE 담당자가 다음 주부터 기획 변경을 당일 공유 채널에 남긴다.’ 팀이 정한 내용을 방장이 정리해 저장하며, 개인별 실행 계획을 추가로 제출하게 하지 않습니다. 항목 수를 강제로 제한하지 않습니다.

다음 차수의 팀 논의를 시작할 때 모아보기에서 이전 Try를 보여줍니다. 팀은 ‘해봤나요? 무엇을 배웠나요?’를 함께 이야기하고, 방장이 그 결과를 선택적으로 짧게 남길 수 있습니다. 결과 메모가 없어도 새 차수의 KPT 제출·회고 완료를 막지 않습니다. 메모는 다음 차수의 팀 논의 기록으로 남기며 이전 차수의 Try 원문·완료 상태를 덮어쓰지 않습니다.

팀의 KPT·실행 항목·실행 결과 메모는 팀 내부 기록입니다. 팀 스타일 지도를 같이 보여주는 기능은 아직 확정하지 않았습니다.

### 4.3 동료 피드백

**동료 피드백**은 특정 동료에게 남기는 기록입니다. 팀의 경험을 돌아보는 KPT와 목적이 다릅니다.

개인의 KPT 제출 완료 화면에 **‘동료에게 피드백 남기기’**와 **‘나중에 하기’**를 제공합니다. 참여하면 해당 차수 팀원 중 본인을 제외한 사람을 선택합니다. 모든 동료에게 쓸 필요는 없고 대상별 건너뛰기도 가능합니다.

| 작성 항목 | 내용 | 필수 여부 |
| --- | --- | --- |
| 도움이 된 순간 | 그 동료가 어떤 상황에서 어떤 행동으로 도움이 됐는지 구체적인 사례 | 사례 1개 필수 |
| 함께 일한 스타일 | 이번 차수에서 관찰한 행동을 6문항에 응답 | ‘관찰하기 어려움’·‘해당 상황 없음’ 응답 허용 |
| 다음에 바라는 점 | 다음 협업에서 기대하는 행동 | 선택 |

스타일 전부를 관찰하기 어려워도 구체적인 사례를 보내면 실제 제출로 인정합니다. 사례가 떠오르지 않으면 그 동료를 건너뛸 수 있습니다. 건너뛰기·나중에 하기·임시저장은 실제 제출로 세지 않습니다. 임의의 글자 수로 품질을 판정하지 않으며, 사례가 있다는 이유만으로 진실성이나 충실함을 보장하지 않습니다.

피드백은 매 차수 제공하지만 **작성은 선택 활동**입니다. 미작성 때문에 개인 KPT 제출 완료나 팀 회고 완료를 취소하지 않습니다. 다만 자신이 받은 피드백을 보는 조건은 따로 있습니다(6.3).

### 4.4 자기 스타일·동료 스타일과 프로필

**스타일**은 이번 차수의 협업에서 보인 업무 행동 빈도입니다. 고정된 성격이나 능력 점수가 아닙니다.

- **자기 스타일:** 개인 KPT 화면 하단의 ‘이번 협업에서 내 모습도 남기기’를 펼쳐 본인이 응답합니다. 선택 항목이며 일부 문항만 답해도 저장하고 미응답은 그대로 표시합니다.
- **동료 스타일:** 선택한 동료의 행동을 피드백 화면에서 응답합니다. 받은 사람에게는 개별 응답이 아니라 조건을 충족한 집계만 보여줍니다.

자기·동료 모두 같은 6가지 행동을 해당 차수 경험 기준으로 묻습니다. 자기 응답은 ‘나는’, 동료 응답은 ‘이 동료는’을 기준으로 읽으며 동료 문항에서는 ‘내 생각’을 ‘자신의 생각’으로 바꿉니다.

| 번호 | 영역 | 자기 응답의 행동 문장 |
| --- | --- | --- |
| 1 | 일 진행 | 작업을 시작하기 전에 목표와 진행 순서를 정리했다. |
| 2 | 일 진행 | 작게 실행해 보고, 결과를 보며 진행 방향을 조정했다. |
| 3 | 공유 | 진행 중인 상황을 중간중간 팀원에게 공유했다. |
| 4 | 공유 | 내용을 정리한 뒤 묶어서 팀원에게 공유했다. |
| 5 | 논의 | 먼저 내 생각이나 대안을 제안했다. |
| 6 | 논의 | 동료의 의견을 들은 뒤 쟁점이나 결론을 정리했다. |

응답은 **거의 안 했어요 / 드물게 했어요 / 가끔 했어요 / 자주 했어요 / 거의 항상 했어요**입니다. ‘해당 상황이 없었어요’와 동료의 ‘관찰하기 어려움’은 별도로 제공하며 빈도·중간값·0점으로 계산하지 않습니다.

결과는 6문항별 유효 응답의 비율로 표시합니다. 각 문항에 서로 다른 동료 3명 이상이 필요합니다. 일 진행·공유·논의는 묶음 이름일 뿐이며, 두 행동을 모두 자주 할 수 있습니다. 영역·종합 점수나 ‘계획형·실행형’ 같은 유형으로 합치지 않습니다. 문항의 측정 신뢰도·타당도는 아직 검증되지 않았습니다.

프로필에서는 프로젝트 정보·본인의 설명과 동료가 관찰한 기록의 출처를 구분합니다. 자기 스타일과 동료 스타일도 하나의 점수로 합치지 않습니다. 기록은 프로젝트 → 차수별로 쌓이며 여러 차수·프로젝트의 스타일을 합산하지 않습니다.

## 5. 처음부터 끝까지의 이용 순서

1. **카카오 로그인:** 프로필에서 이름·직무와 공개 범위를 확인·설정합니다. 직무의 필수 여부는 상세 설계로 남아 있습니다.
2. **프로젝트 생성 또는 초대 수락:** 등록자는 팀원을 초대하고, 참가자는 프로젝트 기본 정보가 연결된 프로필을 갖게 됩니다. 프로젝트별 역할은 선택 입력입니다.
3. **방장이 1차 회고 생성:** 대상 기간과 두 마감을 정합니다. ‘작성 요청 시작’을 누르면 그때 참여 중인 팀원으로 해당 차수 명단을 자동 확정합니다.
4. **각자 KPT 제출:** 자기 스타일은 선택적으로 작성합니다. 제출 직후 원하는 동료에게 피드백을 남기거나 ‘나중에 하기’로 종료합니다.
5. **KPT 마감 후 팀 논의:** 원문을 모아 읽고, 이전 Try가 있으면 함께 돌아보고 결과를 선택적으로 남깁니다. 이번에 실행할 Try를 한 문장씩 정리한 뒤 방장이 회고를 완료합니다.
6. **동료 피드백 마감 후 받은 결과 확인:** 이번 차수의 개인 열람 조건을 충족한 사람에게 결과를 제공합니다. 스타일은 문항별 최소 인원도 확인합니다.
7. **프로필에 공개할 기록 선택:** 기본 정보는 기본 공개이고, 받은 동료 기록·자기 스타일은 본인이 선택해 공개합니다. 공개 프로필은 로그인 없이 읽을 수 있습니다.
8. **다음 주기에 반복:** 방장이 2차 회고를 만들고, 새 차수의 명단·마감·작성·결과를 관리합니다. 다음 팀 논의에서는 이전 Try를 확인합니다.

**5번과 6번은 각 마감에 따라 독립적으로 진행합니다.** 팀 논의가 끝나야 동료 피드백을 쓸 수 있는 흐름이 아닙니다. 기본 공개 프로필은 동료 기록이 생기기 전에도 확인·공유할 수 있습니다.

## 6. 참가자·마감·완료·결과 확인 규칙

### 6.1 프로젝트 참여는 한 번, 회고 명단은 차수마다

프로젝트 초대를 한 번 수락하면 구성원으로 계속 참여합니다. 매 차수 초대를 다시 수락하거나 방장이 같은 사람을 다시 고를 필요는 없습니다. 초대만 받은 사람은 구성원으로 세지 않습니다.

**명단 확정 시점은 프로젝트 생성 때도, 회고 차수를 미리 만들 때도 아닌 ‘작성 요청 시작’입니다.** 시스템이 그때 참여 중인 구성원 명단을 저장하고 KPT 요청·동료 피드백 대상에 함께 사용합니다. 본인은 피드백 대상에서 제외합니다.

예를 들어 1차 요청 때 A·B·C가 참여 중이면 1차 명단은 A·B·C입니다. 이후 D가 합류해도 1차에는 추가하지 않고 다음 차수부터 포함합니다. 미작성자가 있어도 과거 명단·인원은 유지합니다. 첫 출시에서 진행 중 차수 참가자 추가는 제공하지 않습니다.

### 6.2 ‘제출’, ‘마감’, ‘완료’는 다릅니다

| 상태 | 의미 |
| --- | --- |
| 개인 KPT 제출 완료 | 내가 이번 KPT를 보냈다는 뜻 |
| KPT 마감 | 개인 KPT 작성 기간이 끝나 팀이 제출 내용을 모아 볼 시점 |
| 팀 회고 완료 | 팀이 논의한 뒤 방장이 해당 차수를 끝냈다는 뜻. 프로젝트 종료와는 다름 |
| 동료 피드백 마감·공개일 | 동료 피드백 작성 기간 종료와 받은 결과 제공의 공통 시점 |
| 동료 작성 절차 종료 | 나중에 하기·건너뛰기로 끝낼 수도 있음. 실제 제출이나 결과 열람 자격과는 다름 |

KPT 마감과 동료 피드백 마감은 각각 설정하는 항목입니다. 반드시 서로 다른 날짜로 정한다는 뜻은 아닙니다. 두 날짜의 허용 순서·간격은 아직 확정하지 않았습니다. 전원이 일찍 피드백을 끝내도 정한 마감·공개일 전에 결과를 공개하지 않습니다.

### 6.3 받은 피드백은 언제 볼 수 있나요?

**같은 프로젝트의 이번 차수에서 동료 한 명 이상에게 실제 피드백을 제출하고, 그 차수 피드백 공개일이 되어야 합니다.** KPT 제출만으로 받은 동료 피드백이 열리지는 않습니다.

| 내 상태 | 이번 차수의 받은 동료 기록 |
| --- | --- |
| 동료 피드백을 한 건도 제출하지 않음 | 잠김 |
| 한 명 이상에게 제출했지만 공개일 전 | 잠김 |
| 공개일에 유효한 제출이 한 명 이상 있음 | 열람 자격 확정 |
| 공개일 전에 제출한 기록을 모두 삭제함 | 유효 제출이 0건이면 자격을 얻지 못함 |
| 자격 확정 후 본인 제출 기록을 정상적으로 삭제함 | 이미 얻은 그 차수의 자격은 유지. 삭제된 응답은 집계에서 제외 |

1차에서 썼다고 2차 결과가 열리지 않고, 다른 프로젝트의 제출도 대신 사용할 수 없습니다. 내가 쓴 상대의 기록만 열리는 구조는 아닙니다. 조건을 충족하면 이번 차수에 나에게 남겨진 기록을 확인합니다.

- **도움이 된 순간·다음에 바라는 점:** 받은 기록 1건부터 확인합니다. 바라는 점은 받은 사람만 봅니다.
- **동료 스타일:** 문항별로 서로 다른 동료 3명 이상의 유효 응답이 모인 집계만 제공합니다. 비관찰 응답은 계산·분모·최소 인원에서 제외합니다.

스타일이 부족해도 문장형 피드백까지 숨기지 않습니다. 이 조건은 참여를 유도하려는 규칙이며, 형식적인 작성이나 허위 사례를 막는다고 약속하지 않습니다. 열람 가능은 외부 자동 공개를 뜻하지 않습니다.

### 6.4 차수 운영과 마감 이후

방장은 차수를 직접 만들고, 대상 기간·KPT 마감·피드백 마감을 설정합니다. 주기 변경은 앞으로 만드는 차수에 적용합니다. 다음 차수의 팀 논의에서 이전 Try를 보여주고 방장이 팀의 실행 결과·배운 점을 선택적으로 짧게 남깁니다. 결과 메모는 완료 조건이 아니며, 자동 이월·자동 달성 판정·차수 자동 생성은 첫 출시에서 제외합니다.

| 상황 | 처리 |
| --- | --- |
| KPT 마감에 제출이 있음 | 미작성자가 있어도 원문 모아보기로 전환 |
| KPT 제출 0건 | ‘제출 없이 종료’로 표시. 논의·회고 완료로 세지 않음 |
| 논의 후 실행할 Try를 정하지 못함 | 미선정 이유를 남겨 방장이 회고 완료 가능 |
| 방장이 마감을 바꿈 | 해당 마감 전까지만 허용하고 참가자에게 변경 알림 |
| 이미 마감했거나 종료한 차수를 다시 엶 | 첫 출시에서 재개 제공 안 함 |

### 6.5 늦게 참여하거나 ‘나중에 하기’를 선택한 경우

프로젝트 합류는 진행 중에도 허용하지만 차수 작성 요청 이후 합류자는 다음 차수부터 작성합니다. KPT 마감은 프로젝트 가입을 막는 시점이 아닙니다.

‘나중에 하기’ 후에도 동료 피드백 마감 전에는 돌아와 제출할 수 있습니다. 마감 이후 신규 동료 피드백은 받지 않으며 기한을 놓치면 다음 차수에 참여합니다. KPT도 마감 후 신규 제출을 추가하는 예외는 첫 출시 기본 흐름에 두지 않습니다. 상세 실패·복구 처리는 화면 설계에서 정합니다.

### 6.6 수정·삭제·탈퇴

| 대상·상황 | 정한 방향 |
| --- | --- |
| KPT·자기 스타일 | KPT 마감 전 수정 가능. 이후 수정 잠금·삭제 허용 |
| 동료 피드백 | 동료 피드백 마감 전 수정 가능. 이후에도 삭제 허용 |
| 프로젝트의 짧은 역할 | 나중에도 수정 가능 |
| 수신자가 받은 문장을 관리 | 숨김·신고 가능. 다른 사람이 쓴 문장은 직접 수정 불가 |
| 스타일 응답이 삭제됨 | 집계에서 제외하고, 유효 동료가 3명 미만이면 해당 문항 집계를 본인·외부에 제공하지 않음 |
| 프로젝트 나가기·강퇴 | 팀원 전용 열람 종료. 자신의 기록·받은 피드백은 기존 조건에 따라 유지. 과거 확정 명단은 유지하고 이후 차수에서는 제외 |
| 새 팀원이 지난 기록을 읽음 | 합류만으로 지난 차수의 팀 내부 KPT·피드백 권한을 자동 부여하지 않음. 외부 공개 기록은 일반 방문자처럼 확인 |
| 회원 탈퇴 | 공개 프로필·자기 정보·본인이 작성한 개별 기록 삭제 방향. 팀 공동 실행 항목은 식별 정보를 제거해 유지 |

수신자의 문장 숨김을 작성자 기록 삭제나 스타일 응답 삭제로 취급하지 않습니다. 기록을 삭제했다고 이미 진행한 팀 논의·완료 상태를 소급 취소하지 않습니다.

프로젝트 나가기와 회원 탈퇴는 구분합니다. 회원 탈퇴 시 공동 기록·받은 기록·백업의 실제 삭제·보관 범위와 방장 탈퇴 처리는 출시 전 추가 검토가 필요합니다.

## 7. 공개 범위와 표현 보호

### 7.1 어떤 내용이 누구에게 보이나요?

프로필은 **기본 공개**입니다. 최초 입력·프로젝트 참여 때 공개 범위를 표시하고 프로필 비공개 전환·프로젝트별 숨김을 제공합니다.

| 내용 | 공개 범위 |
| --- | --- |
| 이름·직무·프로젝트 이름과 기간·선택적 역할 | 공개 프로필에 기본 포함. 비공개 전환·프로젝트 숨김 가능 |
| 자기 스타일 | 본인이 선택해 외부 공개 |
| 받은 도움이 된 순간 | 차수별 조건을 충족하면 본인 확인. 외부에는 본인이 선택해 공개 |
| 받은 동료 스타일 집계 | 차수·문항별 조건을 충족하면 본인 확인. 외부에는 본인이 선택해 공개 |
| 다음에 바라는 점 | 받은 사람만 확인. 이름 표시 없음 |
| 팀 KPT·팀이 정한 실행 항목·실행 결과 메모 | 팀 내부 기록. KPT 작성자 이름은 팀 내부 표시 |

기본 공개가 모든 기록의 자동 공개를 뜻하지 않습니다. 받은 기록은 프로젝트 → 차수별로 보여주며 스타일을 차수 간 합산하지 않습니다.

공개 프로필은 공개 범위를 관리한 뒤 링크를 복사해 공유합니다. 최초 ‘공개하기’ 단계는 필수가 아닙니다. 비공개 상태에서 공유하려면 공개 범위를 확인하고 공개 전환 후 링크를 복사합니다. 공개·비공개 설정은 유지합니다. 검색엔진 노출은 첫 출시에서 제외합니다.

### 7.2 같은 팀원이 프로필을 보는 경우와 익명성의 한계

팀원 아바타를 클릭하면 같은 개인 프로필 페이지로 이동합니다. 현재 같은 프로젝트 팀원은 공통 프로젝트의 기본 기록과 외부 공개된 기록을 봅니다. 프로필을 비공개로 바꿔도 그 팀원의 기본 기록 열람은 유지합니다. 다른 프로젝트의 비공개 기록이나 받은 피드백 전체를 볼 수 있는 것은 아닙니다. 팀 전용 기록에는 ‘함께 참여한 팀원에게 공개’라고 표시합니다.

열람 조건·공개 시점·최소 인원은 서버에서도 확인하며, 개별 스타일 응답·기준 미달 집계는 받는 사람이나 외부에 전달하지 않습니다. 스타일은 공개 시점에 일괄 집계하고 들어오는 응답마다 그래프를 바꾸지 않습니다. 제한 안내는 스타일 영역에만 표시합니다. 문장형 기록을 같이 숨기지 않습니다.

공개 문장의 작성자 이름은 ‘이*현’처럼 가리는 방향입니다. 구체적인 공개 동의는 추가 설계가 필요합니다. 문장·상황이나 삭제 후 집계 변화로 작성자를 추정할 수 있으므로 ‘완전한 익명’이나 ‘누가 작성하지 않았는지 절대 알 수 없다’고 약속하지 않습니다. 개별 미작성 관계를 직접 제공하지 않는 원칙을 유지합니다. 공개 변경 전에 다른 사람이 저장한 사본까지 회수하지는 못합니다.

원래 팀 규모는 등록자가 입력한 자기 신고 수치입니다. 초대를 수락한 서로 다른 계정 수인 소스바 참여 인원과 구분하며, 현재 구성원과 과거 참여를 구분합니다. 차수 인원은 요청 시작 때 확정한 명단입니다. 미작성·이탈로 과거 인원을 소급 변경하지 않습니다.

피드백 작성자 수는 표시 범위의 서로 다른 계정 수입니다. 같은 동료가 여러 차수·프로젝트에서 남겨도 사람 수는 한 명이며 기록 건수는 늘 수 있습니다. 같은 프로젝트·차수·작성자·수신자 조합은 한 기록으로 보고 수정은 새 건수로 세지 않습니다. 같은 사람의 반복 응답으로 스타일 최소 3명을 채우지 않습니다. 계정 수가 실제 사람·팀 규모의 검증을 뜻하지 않습니다.

### 7.3 AI 다듬기와 신고

AI는 수신자 전용인 **‘다음에 바라는 점’**의 표현을 다듬는 데만 사용합니다. 외부에 공개되는 ‘도움이 된 순간’은 AI로 다듬지 않습니다.

- 상황·행동의 의미를 유지하고 새 사실을 만들지 않는 것을 품질 기준으로 둡니다.
- 제안 문장·원문·직접 수정 중 작성자가 선택한 최종 문장만 전송합니다.
- 오류가 나면 입력을 보존하고 재시도·직접 수정을 제공합니다. 직접 수정도 모욕·인신공격 차단을 우회하지 않습니다.
- 외부 AI에는 다듬을 문장만 보내고 별도 이름·프로젝트 정보는 전달하지 않습니다. 본문에 식별 정보가 있는 경우의 처리는 추가 검토합니다.
- 모든 중간 AI 제안을 보관하지 않고 원문·최종 전송문은 해당 피드백과 함께 관리·삭제합니다.
- 운영자는 신고 처리에 필요한 내용만 검토하고 당사자에게 조치 결과·이의 제기 경로를 제공합니다. 작성자 식별 정보·조치 사유를 공개 프로필에 노출하지 않습니다.

업체의 처리·보관 조건, 모욕 탐지 기준·오탐 대응·운영 담당·신고 보관 기간은 출시 전에 정해야 합니다. AI가 의미를 항상 보존하거나 갈등·유해 표현을 모두 해결한다고 보장하지 않습니다.

### 7.4 프로필 공유 규칙 요약

**기본 정보는 기본 공개, 받은 동료 기록은 조건 충족 후 본인 선택 공개**입니다. 프로필 비공개 전환과 기록별 숨김을 제공하며, 팀 KPT·바라는 점은 외부 공개 대상에 포함하지 않습니다.

같은 프로필 페이지 안에서 방문자의 프로젝트 관계·공개 설정에 따라 허용한 내용만 제공합니다. 링크를 알고 있다는 이유로 팀원 전용 기록을 읽을 수는 없습니다. 프로젝트 이탈 후 전용 열람은 종료합니다.

## 9. 초기 도입과 검증할 가정

부트캠프·교육과정의 팀 프로젝트를 초기 도입 대상으로 합니다. 기관과 협의해 여러 팀에서 사용 과정을 확인할 계획이며, 실제 인터뷰·테스트 결과는 아직 없습니다.

기관에 전달하는 기본 참여 상태는 **팀 단위 KPT 제출 인원과 차수 완료 상태**입니다. 개인별 동료 피드백 작성 여부·원문·스타일은 제공하지 않습니다. 제출 0건의 ‘제출 없이 종료’도 회고 완료와 구분합니다. 기관용 화면·전달 채널은 후속입니다. 공개 프로필을 기관이 읽을 수 없다고 약속하지 않으며 비공개 내용 제공과 평가 활용의 경계를 설명해야 합니다.

검증할 핵심은 ‘작성 부담이 적은가’, ‘동료 기록이 쌓이는가’, ‘프로필을 공유할 가치가 있는가’입니다.

## 10. 잘되고 있는지 확인할 신호

개인 KPT·피드백 제출과 이탈, 도움이 된 순간의 구체성, 프로필 공유·실제 열람, 다음 프로젝트에서 재사용하는지 확인합니다. 제출 수가 많다는 이유만으로 품질이 좋다고 판정하지 않습니다.

개인 KPT·자기 스타일·동료 1명 피드백에 15분이라는 시간 목표 후보를 두었지만 실제 측정값은 아닙니다. 가입·프로젝트 등록·팀 논의·대기 시간은 별도로 보고 실측 후 조정합니다.

## 12. 관리번호는 무엇인가요?

번호는 기획·화면·개발 문서에서 같은 항목을 찾아 연결하기 위한 표식입니다. **번호가 크다고 더 중요하거나 더 우선한다는 뜻은 아닙니다.**

| 표시 | 뜻 | 예시 |
| --- | --- | --- |
| DEC | 제품 결정(Decision) | DEC-24: 기본 공개 프로필과 직무를 채택한 결정 |
| Q | 함께 검토한 질문(Question) | Q-07: 프로필 공개 방식. 방향은 정했고 직무 입력 상세는 남음 |
| F | 사용자 흐름(Flow) | F-01: 카카오 로그인·프로필 확인 단계 |
| U | 대상 사용자(User) | U-01: 팀 프로젝트 참가자 |
| P | 해결하려는 문제(Problem) | P-01: 협업 경험을 개인 기록으로 남기기 어려움 |
| G / NG | 목표(Goal) / 제외할 목표·범위(Non-goal) | G-01: 협업 기록을 프로필에 남기기 |
| AS | 검증할 가정(Assumption) | AS-05: 동료 기록 전에도 초기 프로필 가치가 있는가? |
| M | 확인할 지표(Metric) | M-05: 개인 작성에 실제 걸린 시간 |
| CHK | 출시 점검 항목(Check) | 회원·알림·오류·동의 등 놓치기 쉬운 항목 |

`DEC`는 보통 확정한 결정 기록입니다. 일부는 이전 결정을 구체화하거나 대체했으므로 현재 제품 규칙은 이 문서 본문을 기준으로 읽습니다. `Q`는 질문에 붙인 번호여서, 번호가 남아 있어도 큰 방향이 이미 해결됐을 수 있습니다.

처음 읽는 사람은 이 **서비스 기획서 하나**를 먼저 읽으면 됩니다. 더 자세히 확인할 때에는 다음 자료를 사용합니다.

- [서비스 공통 기준·결정 이력](00-service-context.md): 서비스의 공통 기준과 전체 결정 이력.
- [용어 사전](00-glossary.md): 서비스 용어의 쉬운 설명과 기획 연결표.

<details>
<summary>제품 결정 번호와 본문 연결표 펼치기</summary>

| 본문 내용 | 관련 제품 결정 번호 |

## 14. 참고 자료와 적용 경계

- 사용자 제공 「소스바(Sossbar) 소개」와 2026-10-05~06 대화: 제품 방향과 결정의 출처.
- [캔디드 — KPT 회고: 스타트업이 실패를 자산으로 바꾸는 방법(+템플릿)](https://teamcandid.kr/blog/kpt-retrospective-guide): 2025-09-23 게시, 2026-10-06 확인. KPT 작성·팀 논의·실행과 다음 회고의 연결을 참고.

### 14.1 현재 기획을 검토한 결과

아래는 참고 글과 소스바 기획을 비교한 판단입니다. 2026-10-06 사용자 결정으로 작성 안내·팀 Try 한 문장·다음 차수의 선택적 결과 메모를 첫 출시 범위에 반영했습니다. 글의 권고 전체를 제품의 필수 입력 규칙으로 채택한 것은 아닙니다.

| 검토 항목 | 현재 기획과 판단 |
| --- | --- |
| 반복 회고 | 글은 정기 회고와 프로젝트 종료 후 회고 등을 소개합니다. 팀이 주기를 정하고 여러 차수를 운영하는 현재 방향과 맞습니다. 글의 주기를 서비스의 고정 주기로 사용할 필요는 없습니다. |
| 작성과 팀 논의 | 글의 템플릿은 KPT 작성과 실행 항목 정리를 구분합니다. 소스바의 개인 작성 → 원문 모아보기 → 팀 논의 → 실행할 Try 선택 흐름과 맞습니다. 작성만으로 회고가 끝났다고 처리하지 않는 방향을 유지합니다. |
| 구체적인 KPT | 글은 행동·결과, 문제 원인, 실행 가능한 계획과 비난보다 개선을 강조합니다. 소스바는 쉬운 질문·예시를 제공하고, 숫자·원인 분석을 필수로 요구하지 않는 방향을 확정했습니다. |
| Try 실행과 다음 회고 | 글은 담당자·기한·확인 기준과 다음 회고에서의 실행 점검을 강조합니다. 소스바는 팀의 Try를 한 문장으로 남기고 다음 차수에서 결과를 선택 기록하는 범위로 채택했습니다. 담당자·기한은 별도 입력칸이나 필수 조건으로 두지 않습니다. |
| 글의 수치·운영 기준 | 숫자 포함, 실행 항목 3개 이하 등의 기준은 해당 글의 운영 권고로 참고합니다. 소스바에서는 구체적인 상황·행동도 유용하므로 숫자나 항목 수를 필수로 강제하는 규칙으로 바로 채택하지 않습니다. |

### 14.2 채택한 보완 범위

1. **개인 KPT는 쉬운 질문과 예시로 지원:** 구체적인 상황·행동을 안내하되 숫자·원인 분석이나 개인별 실행 계획을 추가로 요구하지 않습니다.
2. **팀이 선택한 Try는 한 문장으로 작성:** 방장이 팀의 결정을 정리하며 ‘누가 언제 무엇을 할지’를 예시로 안내합니다. 담당자·기한·확인 기준을 별도 입력칸이나 각각의 필수 항목으로 추가하지 않습니다.
3. **다음 회고에서 이전 Try를 확인:** 팀 논의의 시작에 이전 행동을 돌아보고, 방장이 결과·배운 점을 선택적으로 짧게 기록합니다. 추가 보고·결과 메모를 회고 완료 조건으로 요구하지 않으며 자동 이월·자동 달성 판정은 제공하지 않습니다.

이 글은 KPT 운영 참고 자료이며, 소스바의 개인별 동료 피드백을 필수 절차로 요구하는 근거는 아닙니다. 참가자 명단 확정·작성 마감·프로필 공개·열람 자격·스타일 최소 인원은 소스바에서 정한 제품 규칙입니다. 글의 운영 권고와 확정된 제품 결정을 구분합니다.
