# 제품 디자인 공통 원칙

모든 디자인 스킬과 에이전트는 이 원칙을 따른다.

## 1. 제품 근거에서 시작한다

- 디자인 결정은 관련 문제 `P-*`, 목표 `G-*`, 흐름 `F-*`, 정책 `POL-*`, 화면 요구사항 `SCR-*` 중 하나 이상과 연결한다.
- 참고 디자인 시스템의 값이나 형태를 근거 없이 복제하지 않는다.
- 상위 기획이 없으면 작업을 중단하지 않고 가정과 결정 필요를 분리한 초안을 만든다.

## 2. 키워드를 행동 원칙으로 바꾼다

- `신뢰`, `친근함`, `간결함`처럼 일반적인 단어만으로 시각 결정을 확정하지 않는다.
- 키워드마다 필요한 이유, 사용자에게 보일 행동, 하지 않을 것, 충돌 시 우선순위를 정의한다.
- 색상이나 서체 선택은 키워드와 자동으로 일대일 대응한다고 가정하지 않는다.

## 3. 시스템과 화면의 책임을 구분한다

- 디자인 시스템은 반복 가능한 토큰, 컴포넌트, 콘텐츠와 상호작용 규칙을 정의한다.
- 제품 UI는 특정 사용자 목표를 위한 정보 구조, 위계, 레이아웃과 컴포넌트 조합을 정의한다.
- 화면 하나의 요구만으로 공통 토큰이나 컴포넌트를 추가하지 않는다.

## 4. 모든 상태를 계약으로 다룬다

- 기본, 호버, 포커스, 누름, 선택, 비활성, 읽기 전용, 로딩, 성공, 오류 상태 중 관련 항목을 정의한다.
- 로딩, 빈 상태, 입력 오류, 요청 실패, 권한 없음, 긴 콘텐츠와 반응형 상태를 화면 명세에 포함한다.
- 사용자에게 보이는 결과와 시스템 처리를 구분한다.

## 5. 의미 기반 토큰을 우선한다

- 원시 값, 의미 역할, 컴포넌트 적용 계층을 구분한다.
- 화면과 컴포넌트에서 임의의 원시 값을 직접 사용하지 않는다.
- 테마나 브랜드 변경이 의미 토큰 교체로 전파될 수 있게 한다.

## 6. 콘텐츠도 시스템의 일부다

- 버튼, 필드, 오류, 빈 상태, 알림과 위험 행동의 문구 패턴을 컴포넌트 규칙과 연결한다.
- 친근한 표현이 결과, 위험, 금액, 기한이나 복구 방법을 가리지 않게 한다.
- 서비스 용어와 사용자 노출 용어가 다르면 용어 사전에 기록한다.

## 7. 접근성을 사후 점검으로 미루지 않는다

- 색상 대비, 키보드 조작, 포커스 순서, 레이블, 오류 전달, 모션 감소를 설계 시점에 정의한다.
- 색상만으로 상태나 의미를 전달하지 않는다.
- 접근성 기준을 충족했다고 주장하려면 대상 플랫폼과 검증 근거를 기록한다.

## 8. 시스템 공백을 추적한다

- 기존 컴포넌트 조합으로 해결되지 않는 요구는 `GAP-*`로 기록한다.
- 공백은 `기존 컴포넌트 활용`, `기존 컴포넌트 확장`, `신규 공통 컴포넌트`, `화면 전용 패턴` 중 하나로 판정한다.
- 디자인 시스템 변경 시 영향받는 화면과 개발 계약을 다시 확인한다.
- 공백 상태는 `발견 → 분류 완료 → 시스템 반영 → UI 재적용 → 검증 완료`로 전이한다. 보류하거나 기각하면 이유와 임시 처리 여부를 기록한다.
- 사용자 결과나 공통 계약을 바꾸는 미해결 Blocker/Major 공백이 있으면 개발 인계를 `Blocked`로 표시한다.
