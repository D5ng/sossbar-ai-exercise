# 기획·디자인·개발 인계 계약

각 단계가 다음 단계에 무엇을 전달하며, 무엇을 임의로 결정할 수 없는지 정의한다.

## 식별자

| 영역 | 접두사 | 예시 |
| --- | --- | --- |
| 문제·목표 | `P`, `G` | `P-01`, `G-01` |
| 흐름·정책·화면 | `F`, `POL`, `SCR` | `F-01`, `POL-01`, `SCR-01` |
| 디자인 키워드·원칙 | `KW`, `DP` | `KW-01`, `DP-01` |
| 토큰·컴포넌트 | `TOK`, `CMP` | `TOK-01`, `CMP-01` |
| UI·문구 | `UI`, `COPY` | `UI-01`, `COPY-01` |
| 시스템 공백 | `GAP` | `GAP-01` |
| 인계·검토 | `HOF`, `DREV`, `A11Y` | `HOF-01`, `DREV-01`, `A11Y-01` |
| 가정·리서치 | `AS`, `RS`, `RQ`, `PT`, `INS`, `T`, `UT`, `REC` | `AS-01`, `INS-01`, `UT-01` |

## PM/PO에서 디자인으로

반드시 확인할 입력:

- 우선 사용자, 문제와 제품 목표
- MVP 포함·제외 범위
- 정상·분기·실패·복구 흐름
- 정보 구조(IA): 페이지 계층, 내비게이션, 페이지별 접근 조건
- 역할, 권한, 상태와 입력 정책
- 화면 목적과 관찰 가능한 성공 조건
- 용어 사전과 확정·가정·결정 필요 상태

디자인은 미확정 정책을 시각 요소나 문구로 확정하지 않는다. 정책이 없더라도 안전한 초안은 만들 수 있지만, 영향을 받는 항목에 상태를 표시한다.

## 디자인 시스템에서 제품 UI로

반드시 확인할 입력:

- 디자인 키워드와 행동 원칙
- Foundation과 의미 기반 토큰
- 컴포넌트의 목적, Anatomy, Variant, State와 사용 규칙
- 공통 콘텐츠, 접근성, 반응형과 모션 규칙
- 사용 중지 또는 교체 예정 항목

UI 설계자는 임의 토큰이나 공통 컴포넌트를 만들지 않는다. 시스템에서 해결할 수 없는 요구는 `GAP-*`로 반환한다.

## 제품 UI에서 개발로

개발 인계에는 다음을 포함한다.

- 화면별 정보 위계, 레이아웃과 반응형 규칙
- UI 명세 경로와 시각 UI가 있다면 `visual-index.md`, 디자인 파일·페이지·노드 식별자와 검증 상태
- 사용한 컴포넌트, Variant, State와 토큰 참조
- 사용자 행동에 따른 전환과 피드백
- 로딩, 빈 상태, 오류, 권한, 긴 콘텐츠와 중복 행동
- 최종 UX 문구와 접근성 요구사항
- 디자인 시스템 공백, 미결정 정책과 구현 제외 범위
- 관련 `AC-*`, `EVT-*`와 확인 방법

개발 하네스는 디자인 인계만 보지 않고 관련 정책, AC와 트래킹 플랜을 함께 읽는다. 개발 기술 스택, API와 코드 구조는 개발 하네스가 추가된 뒤 별도 계약으로 확장한다.

## 시스템 공백 상태

| 상태 | 의미 | 다음 단계 |
| --- | --- | --- |
| 발견 | UI에서 기존 시스템으로 해결되지 않음 | 시스템 담당 분류 |
| 분류 완료 | 활용·확장·신규·화면 전용 중 판정됨 | 필요한 설계 반영 |
| 시스템 반영 | 토큰·컴포넌트 또는 화면 전용 규칙에 반영됨 | UI 재적용 |
| UI 재적용 | 실제 화면 명세 또는 시각 산출물에 반영됨 | 접근성·정합성 검증 |
| 검증 완료 | 관련 검토를 통과함 | 개발 인계 가능 |
| 보류·기각 | 현재 범위에 반영하지 않음 | 이유와 임시 처리 기록 |

미해결 Blocker/Major 공백이 있으면 인계 문서는 만들 수 있지만 준비 상태는 `Blocked`다. `Ready for Dev`는 관련 공백이 검증 완료됐거나 범위에서 명시적으로 제외된 경우에만 사용한다.

## 리서치에서 기획·디자인으로

리서치 결과는 원문을 직접 바꾸지 않고 반영 제안(`REC-*`)으로 전달한다. 사용자가 채택한 제안만 반영한다.

| 결과 | 전달 대상 | 반영 방식 |
| --- | --- | --- |
| 가정 판정, 인사이트 | 기획서 `AS-*`, `P-*` | `service-planning` 부분 재실행 |
| 사용성 문제 중 정책·흐름·정보가 원인인 것 | 정책서, 유저 플로우, 화면 요구사항 정의서 | `service-planning` 부분 재실행 |
| 사용성 문제 중 배치·문구·컴포넌트가 원인인 것 | UI 명세, `COPY-*`, `GAP-*` | `product-design` 부분 재실행 |

사용자가 제공한 기록에 근거하지 않은 리서치 결과는 `사실`로 쓰지 않는다.

## 변경 영향

| 변경 | 다시 확인할 영역 |
| --- | --- |
| 제품 목표·정책·흐름·정보 구조 | 디자인 브리프, UI, 문구, 검토 |
| 디자인 키워드·원칙 | Foundation, 컴포넌트, 문구, UI |
| 토큰·컴포넌트 | 사용 화면, 접근성, 개발 인계 |
| UI 흐름·상태 | 문구, 접근성, AC, 개발 인계 |
| 개발 제약 | 토큰 배포, 컴포넌트 API, UI 실현 가능성 |
| 리서치 반영 제안 채택 | 제안이 가리키는 문서와 그 하위 문서 |
