# 브리프 보강 제안

틀린 곳은 없지만 얇은 기획 초반 문서에서 빠진 관점을 찾아 제안으로 돌려준다. 이 스킬은 내용을 대신 채우지 않고, 사용자가 채택할지 고를 선택지를 만든다.

## 다른 역할과의 경계

| 요청 | 담당 |
| --- | --- |
| 무엇을 더 넣으면 좋을지 제안 | 이 스킬 |
| 브리프를 직접 고치거나 다시 써 달라 | `service-planning`을 거쳐 `product-brief` |
| 회원·운영·법적 고지·시스템 화면·알림·비기능 같은 출시 기반 항목 판정 | `product-brief`의 공통 점검(`web-service-checklist.md`) |
| 문서 사이의 누락·모순·검증 불가 | `spec-reviewer` |
| 흐름·정책·화면의 예외·상태 누락 | `spec-reviewer`의 완전성 기준 |

공통 점검 목록은 출시에 필요한 기반을 판정하는 도구이고, 이 스킬은 문제·사용자·가치·범위를 넓히거나 좁히는 도구다. 공통 점검의 `CHK-*` 항목을 제안으로 다시 올리지 않는다.

## 입력 확인

- 브리프가 있으면 브리프를, 없으면 사용자가 제공한 아이디어 문장을 대상으로 한다.
- 대상이 전혀 없으면 서비스 아이디어를 한 문장만 요청하고 멈춘다.
- 사용자가 특히 궁금해하는 영역이 있으면 그 관점을 먼저 본다.
- `확정` 상태이거나 결정 기록에 있는 항목은 뒤집는 제안을 하지 않는다. 확정 결정과 충돌하는 큰 위험을 발견하면 `제안 대신 질문`에만 남긴다.

## 작업 절차

1. 섹션별로 얼마나 얇은지 진단한다.
2. 아래 관점을 모두 적용해 제안 후보를 모은다.
3. 근거 위치가 없는 후보, 일반론, 공통 점검 항목과 겹치는 후보를 버린다.
4. 남은 후보를 우선순위로 정렬하고 우선 제안 5~10개를 고른다.
5. 사용자만 답할 수 있는 항목은 제안이 아니라 질문으로 옮긴다.

### 1. 얇은 곳 진단

| 브리프 섹션 | 얇다는 신호 |
| --- | --- |
| 문제와 사용자 | 문제가 하나이고 상황이 추상적이다. 사용자 유형이 하나로 뭉뚱그려져 있다. 현재 대안이 비었거나 `없음`이다. |
| 목표와 제외 범위 | `NG-*`가 없다. 목표가 기능 이름으로 쓰여 있다. |
| 가치 제안 | 현재 대안과 비교한 차이가 드러나지 않는다. |
| MVP 범위 | 모든 후보가 `포함`이다. 판단 이유가 비어 있다. |
| 성공 신호 | 가입 수 같은 활동량만 있다. 확인할 가설과 연결되지 않는다. |
| 가정과 검증 | 가정이 한두 개뿐이다. 검증 방법이 `조사`처럼 막연하다. |
| 제약 조건 | 비어 있다. |
| 공통 점검 | 판정 없이 비어 있는 영역이 있다. 이 경우 제안을 만들지 않고 진단 요약에 `product-brief 공통 점검 판정 필요`로만 적는다. |

### 2. 제안 관점

| 관점 | 확인할 질문 |
| --- | --- |
| 사용자 확장 | 돈을 내는 사람과 쓰는 사람이 다른가? 양면 서비스라면 반대편 사용자는 누구인가? 두 번째로 중요한 사용자층이 있는가? |
| 상황 구체화 | 문제는 언제, 어디서, 얼마나 자주 생기는가? 사용자가 서비스를 떠올리는 계기는 무엇인가? |
| 현재 대안 | 사용자는 지금 실제로 무엇으로 버티는가? 그 대안의 좋은 점과 옮겨 올 때 드는 비용은 무엇인가? |
| 생애주기 | 첫 가치를 경험하기까지 무엇이 필요한가? 다시 올 이유와 떠날 이유는 무엇인가? |
| 공급·초기 상태 | 서비스 안의 콘텐츠나 공급은 누가 채우는가? 처음에 비어 있는 상태를 어떻게 넘기는가? |
| 신뢰 | 사용자 사이의 신뢰 부족이 핵심 가치를 무너뜨릴 수 있는가? 그렇다면 가치 제안이나 MVP 범위가 달라지는가? 신고·차단·약관 같은 기반 기능은 공통 점검에서 다룬다. |
| 비즈니스 | 누가 비용을 내는가? 사용자가 늘면 어떤 비용이 함께 늘어나는가? |
| 범위 좁히기 | 명시적으로 하지 않을 것은 무엇인가? MVP에서 빼도 핵심 가치가 유지되는 기능은 무엇인가? |
| 가정 검증 | 틀리면 서비스가 성립하지 않는 가정은 무엇인가? 그 가정을 가장 적은 비용으로 확인하는 방법은 무엇인가? |

모든 관점을 검토하되, 대상 문서에 근거가 있는 후보만 제안으로 남긴다.

### 3. 제안 유형

| 유형 | 의미 |
| --- | --- |
| 채우기 | 기존 섹션의 빈 칸이나 얇은 항목에 넣을 내용 후보 |
| 넓히기 | 새 사용자, 문제, 상황 후보 |
| 좁히기 | 제외 범위나 MVP 제외 후보. 보강이 항상 추가를 뜻하지는 않는다. |

### 4. 우선순위

- 높음: 틀리면 핵심 사용자·문제·가치 제안·MVP 범위가 바뀐다.
- 중간: IA·흐름·정책 작성 전에 정해 두면 재작업이 줄어든다.
- 낮음: 나중에 반영해도 상위 결정이 바뀌지 않는다.

## 제안 규칙

- 모든 제안에는 근거 위치가 있다. 브리프의 섹션·ID를 적거나 사용자 입력을 인용한다.
- 서비스 이름을 다른 서비스로 바꿔도 그대로 성립하는 조언은 일반론이므로 제안하지 않는다.
- 문제·목표와의 연결에 따라 분류한다. 기존 `P-*`/`G-*`에 연결되면 `MVP 보강`, 새 문제를 여는 제안이면 `문제 후보`, 현재 목표와 연결되지 않으면 `후속 후보`로 둔다.
- 제안 내용의 정보 상태는 기본적으로 `가정`이다. 시장 수치, 경쟁사 정보, 법적 의무는 출처와 확인일이 있을 때만 `사실`로 쓰고, 없으면 `확인 필요`로 둔다.
- 사용자가 명시적으로 찾아 달라고 하지 않으면 경쟁사·시장 조사는 하지 않는다. 필요해 보이면 `제안 대신 질문`에 조사 여부를 묻는다.
- 우선 제안은 10개를 넘기지 않는다. 나머지는 `추가 후보`에 한 줄씩 적는다.
- 원문 브리프와 서비스 컨텍스트를 수정하지 않는다.

## 출력 형식

기본 저장 위치는 `planning/01a-brief-enrichment.md`다.

```markdown
# {서비스명} 브리프 보강 제안

- 대상: {파일 경로 또는 `사용자 입력`}
- 작성일: {YYYY-MM-DD}
- 이전 제안: {없음 / 채택 n · 보류 n · 거절 n}

## 1. 진단 요약

| 브리프 섹션 | 밀도 | 얇은 이유 |
| --- | --- | --- |
| 문제와 사용자 | 충분/보통/얇음 | ... |

가장 얇은 곳: {한두 문장}

## 2. 우선 제안

### SUG-01 [넓히기] {제안 제목}

- 근거: {브리프 섹션·ID 또는 사용자 입력 인용}
- 관점: {제안 관점}
- 제안: {무엇을 추가·변경·제외할지 구체적으로}
- 이유: {이게 없으면 생기는 문제와 연결되는 P-*/G-*}
- 분류: MVP 보강 / 문제 후보 / 후속 후보
- 우선순위: 높음 / 중간 / 낮음
- 정보 상태: 가정 / 사실(출처·확인일) / 확인 필요
- 채택 시 반영 위치: {브리프 섹션, 새 ID 후보}. 하위 문서가 있으면 영향 문서도 적는다.
- 확인 방법: {이 제안이 맞는지 가장 적은 비용으로 확인하는 방법}
- 판단: 대기

## 3. 추가 후보

- SUG-11 [채우기] {한 줄 요약} — 근거: {위치}

## 4. 제안 대신 질문

- [ ] {질문} — 답에 따라 달라지는 것: {범위}

## 5. 이번에 보지 않은 관점

- {관점}: {이유. 예: 확정된 결정, 입력 부족}
```

`판단`은 `대기`, `채택`, `보류`, `거절`, `반영됨 → {ID}` 중 하나다.

## 채택과 반영

- 사용자가 채택한 제안은 `service-planning`의 부분 재실행으로 반영한다. 브리프 변경으로 처리하므로 하위 문서가 있으면 그 스킬의 영향 범위 표에 따라 확인한다.
- 반영이 끝나면 제안 문서의 `판단`을 `반영됨 → {새 ID}`로 바꾼다.
- 채택 전에는 어떤 제안도 브리프나 서비스 컨텍스트에 넣지 않는다.

## 재실행

- 이전 제안 문서가 있으면 기존 `판단` 상태를 보존한다.
- `거절`된 제안은 같은 내용으로 다시 올리지 않는다.
- 새 제안은 기존 번호에 이어서 붙인다.
- 브리프가 바뀌어 기존 제안의 근거가 사라졌으면 `판단`을 바꾸지 말고 근거가 사라졌다고 표시한다.

## 완료 기준

- 모든 우선 제안에 근거 위치가 있다.
- 일반론이 없다.
- 공통 점검 `CHK-*` 항목과 겹치는 제안이 없다.
- 추가만이 아니라 좁히기 관점도 검토했다.
- 출처 없는 시장·경쟁·법적 정보를 사실로 쓰지 않았다.
- 원문을 수정하지 않았다.

## 테스트 시나리오

### 정상 흐름

브리프에 문제가 `P-01` 하나뿐이고 현재 대안이 비어 있으며 모든 기능이 MVP에 포함돼 있다. 현재 대안을 채우는 제안, 두 번째 사용자층을 넓히는 제안, MVP 제외 후보를 좁히는 제안을 각각 근거 위치와 함께 낸다.

### 아이디어만 있는 흐름

사용자가 `동네 사람끼리 물건을 빌리는 서비스`만 제공한다. 브리프 없이 이 문장을 근거로 삼는다. 빌려주는 사람의 동기, 파손·미반납이 신뢰를 무너뜨리는 문제, 초기에 물건이 없는 문제를 제안하되 모두 `가정`이나 질문으로 남기고 시장 수치를 만들지 않는다.

### 공통 점검 경계 흐름

브리프의 공통 점검에서 회원·계정과 알림 영역이 비어 있다. 로그인 방식이나 알림 채널을 제안으로 만들지 않고, 진단 요약에 `product-brief 공통 점검 판정 필요`로만 적는다.

### 재실행 흐름

이전에 `SUG-03`을 거절했다. 다시 실행해도 같은 제안을 올리지 않고, 채택된 제안의 반영 여부만 확인한 뒤 새 제안에 `SUG-12`부터 번호를 붙인다.

### 경계 흐름

사용자가 `브리프 보완해서 다시 써줘`라고 요청하면 이 스킬을 쓰지 않고 `service-planning`으로 처리한다.
