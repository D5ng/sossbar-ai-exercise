# 정보 구조(IA) 설계

서비스에 어떤 페이지가 있고, 어떤 계층과 메뉴로 묶이며, 누가 어디에 들어갈 수 있는지를 한 문서로 정리한다. IA가 서비스 전체의 지도라면 사용자 흐름은 그 지도 위에서 목표를 이루는 경로다. IA를 먼저 정하고, 흐름은 IA의 화면 ID를 사용한다. 핵심 기능 화면뿐 아니라 공통 페이지(계정, 법적 고지, 오류, 관리자 영역)도 판정 결과와 함께 이 문서에 드러낸다.

## 참조

- `../../../references/planning-principles.md`
- `../../../references/web-service-checklist.md`
- `../../../references/service-context.md`
- `../../../references/glossary.md`
- 제품 브리프가 있으면 먼저 읽는다. 브리프의 MVP 범위와 `공통 점검` 판정이 IA의 출발점이다.
- 사용자 흐름이 이미 있으면(부분 재실행) 흐름의 `필요한 화면` 목록과 `신규` 표시 화면도 읽는다.

## 입력 확인

- MVP 포함 기능과 제외 범위
- 사용자 역할과 역할별 접근 범위
- 브리프의 `공통 점검` 판정 결과
- 기존 사용자 흐름이 있으면 흐름별 필요한 화면과 `신규` 표시 화면
- 기존 서비스가 있으면 현재 메뉴 구조와 페이지 목록

브리프가 없으면 사용자 자료에서 기능 후보를 도출하되, 각 화면을 `가정`으로 표시한다.

## 설계 절차

1. 브리프의 MVP 포함 기능마다 사용자가 그 기능을 쓰는 데 필요한 화면 후보를 도출한다. 한 화면이 여러 기능을 맡거나 한 기능이 여러 화면에 걸칠 수 있다.
2. 공통 점검에서 `포함`으로 판정된 페이지를 추가한다. 판정되지 않은 항목은 임의로 추가하지 않고 `결정 필요`로 남긴다.
3. 페이지를 사용자 목적 단위의 영역으로 묶고 계층(뎁스)을 정한다.
4. 전역 메뉴, 사용자 메뉴, 푸터에 어떤 페이지를 연결할지 정한다.
5. 페이지별 접근 조건과 권한이 없을 때의 처리를 정리한다. 정책이 없으면 임의로 정하지 않고 `결정 필요`로 남긴다.
6. 흐름이 이미 있으면 흐름의 화면과 대조한다. 흐름에서 `신규`로 올라온 화면을 반영하고, IA에만 있고 진입 경로나 존재 이유가 없는 화면을 점검한다. 흐름이 아직 없으면 `흐름 대조`를 `흐름 작성 후 갱신`으로 남긴다.
7. 화면 ID를 새로 부여하거나 합쳤으면 대조표를 남긴다.
8. 페이지 목록을 완성한 뒤 사이트맵 트리로 요약한다.

## 화면 ID 규칙

- IA는 서비스 전체 화면 ID의 기준 목록이며 `SCR-*`를 처음 부여한다.
- 흐름과 화면 정의서는 IA의 ID를 사용한다. 흐름에서 `신규`로 올라온 화면은 기존 번호에 이어 붙인다.
- ID를 바꾸거나 합치면 `흐름 대조`에 이전 ID와 새 ID를 기록하고 흐름과 화면 정의서를 다시 확인 대상으로 올린다.

## 출력 형식

````markdown
# {서비스명} 정보 구조(IA)

## 1. 범위

| 항목 | 내용 |
| --- | --- |
| 대상 | 서비스 전체 / {기능 영역} |
| 사용자 역할 | {비회원, 회원, 관리자 등} |
| 관련 목표 | G-01 |
| 제외 범위 | {MVP에서 제외한 영역} |

## 2. 사이트맵

```text
{서비스명}
├─ {영역}
│  ├─ SCR-01 {화면명}
│  │  └─ SCR-02 {하위 화면명} (회원)
│  └─ SCR-03 {화면명}
├─ 계정
│  └─ SCR-{NN} {화면명} (회원)
├─ 시스템
│  └─ SCR-{NN} {오류·점검 안내}
└─ 관리자
   └─ SCR-{NN} {화면명} (관리자)
```

## 3. 페이지 목록

| 화면 ID | 화면명 | 뎁스 | 상위 화면 | 구분 | 접근 조건 | 진입 경로 | 근거 | 상태 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| SCR-01 | ... | 1 | - | 핵심/계정/고객지원/법적 고지/시스템/관리자 | 전체/회원/관리자 | 전역 메뉴/링크/알림/직접 접근 | {MVP 기능·G-01} 또는 CHK-*, 흐름 작성 후 F-* 추가 | 확정/가정/결정 필요 |

## 4. 내비게이션

| 위치 | 항목(작업용 레이블) | 연결 화면 | 노출 조건 | 비고 |
| --- | --- | --- | --- | --- |
| 전역 메뉴 | ... | SCR-01 | 전체/로그인 시 | ... |
| 사용자 메뉴 | ... | ... | ... | ... |
| 푸터 | ... | ... | ... | ... |

## 5. 접근 제어

| 화면 ID | 비회원 | 회원 | 관리자 | 권한이 없을 때 | 관련 정책 |
| --- | --- | --- | --- | --- | --- |
| SCR-01 | 가능/불가 | 가능/불가 | 가능/불가 | 로그인 유도/접근 제한 안내/다른 화면으로 이동 | POL-01 또는 결정 필요 |

## 6. 흐름 대조

| 점검 | 결과 |
| --- | --- |
| 흐름에서 `신규`로 올라온 화면 | 흐름 작성 후 갱신 / 없음 / {화면 ID와 반영 여부} |
| IA에만 있고 흐름이 없는 화면 | 흐름 작성 후 갱신 / 없음 / {화면 ID와 존재 이유(CHK-* 등)} |
| 화면 ID 변경·통합 | 없음 / {이전 ID → 새 ID} |

## 7. 결정 필요

- [ ] {질문} — 영향: {화면 ID·흐름·정책}
````

역할 열은 서비스의 실제 역할에 맞게 바꾼다. 사이트맵 트리는 `../../../references/planning-principles.md`의 그림 규칙을 따른다. 접근이 제한된 화면은 줄 끝에 `(회원)`, `(관리자)`처럼 표시하고, 트리가 길면 영역 단위로 나눈다. 트리는 페이지 목록 표를 대신하지 않는다.

## 작성 원칙

- 메뉴·화면 이름은 작업용 레이블이다. 최종 노출 문구는 UX Writer가 `COPY-*`로 확정한다.
- 메뉴의 시각 형태와 배치는 정하지 않는다. `product-ui-design`이 IA를 입력으로 결정한다.
- URL 경로와 라우팅 구조는 개발 결정이므로 확정하지 않는다. 기존 서비스의 URL이 있으면 참고 정보로만 적는다.
- 뎁스가 깊어져 진입 단계가 늘어나는 화면은 그렇게 둔 이유를 적는다.
- 역할은 `references/glossary.md`의 역할 목록과 같은 이름을 쓴다.

## 완료 기준

- 모든 MVP 기능이 적어도 하나의 화면에 배치된다.
- 모든 화면에 구분, 접근 조건, 진입 경로, 근거가 있다. 진입 경로가 없는 화면이 없다.
- 공통 점검에서 `포함`된 페이지가 빠지지 않고, 판정되지 않은 페이지를 사실처럼 추가하지 않는다.
- 흐름 문서가 있으면 흐름의 화면 ID와 대조되어 있고, 없으면 `흐름 대조`가 갱신 대상으로 남아 있다.
- 접근 제어가 정책의 권한 매트릭스와 충돌하지 않거나, 충돌이 `결정 필요`로 남아 있다.
- 사이트맵 트리의 화면 ID·계층·접근 표시가 페이지 목록과 일치한다.
