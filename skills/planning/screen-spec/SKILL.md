# 화면 요구사항 정의서 작성

화면 하나를 개발·디자인·QA가 같은 방식으로 이해할 수 있는 명세로 만든다. 요구사항이 모호하면 사실·가정·결정이 필요한 질문을 구분한다. 사용자가 결정하지 않은 규칙을 확정하지 않는다.

화면에 무엇이 필요하고 어떻게 동작해야 하는지를 정하는 기획 문서다. 와이어프레임과 배치는 디자이너가 디자인 단계의 `product-ui-design`에서 이 문서를 입력으로 그린다.

## 참조

- `../../../references/planning-principles.md`
- `../../../references/service-context.md`
- `../../../references/glossary.md`
- `../../../references/web-service-checklist.md` (브리프 공통 점검에서 `포함`된 규칙 확인용)
- 관련 제품 브리프, 사용자 흐름, 정보 구조(IA)가 있으면 먼저 읽는다. 권한은 IA 접근 제어를 따른다.

## 먼저 확인할 정보

가능한 범위에서 다음을 파악한다. 정보가 없으면 문서의 `가정 및 확인 필요`에 남긴다.

- 화면 이름과 목적: 이 화면에서 사용자가 완료해야 하는 일
- 진입 경로와 종료 경로: 이전/다음 화면, 취소·뒤로가기 흐름. IA가 있으면 IA의 상위 화면·진입 경로와 맞춘다.
- 대상 사용자와 권한: 비회원, 회원, 관리자 등
- 다루는 데이터와 핵심 규칙: 필수값, 수정 가능 여부, 저장·제출 조건
- 연결된 화면·기능, 다른 화면 정의서에 이미 있는 규칙(`SCR-*-R*`)

## 출력 형식

아래 순서로 Markdown 문서를 작성한다. 정보가 충분하지 않은 항목은 추측으로 채우지 말고 `확인 필요`로 표시한다.

```markdown
# {화면명} 화면 요구사항 정의서

| 항목 | 내용 |
| --- | --- |

| 핵심 행동 | {이 화면에서 사용자가 해야 할 가장 중요한 행동 하나} |
| 대상 사용자 | {역할 및 접근 조건} |
| 진입 경로 | {이전 화면·딥링크·트리거} |
| 완료 후 흐름 | {성공·취소·뒤로가기 시 이동} |
| 관련 요구사항 | {G-01, F-01, CHK-* 등} |

## 2. 사용자 흐름

| 상태 ID | 상황 | 발생 조건 | 사용자에게 보이는 상태 | 가능한 행동 | 처리·복구 규칙 |

## 6. 화면 규칙

화면에 보이지 않지만 동작을 결정하는 규칙이다. `주체 + 조건 + 규칙 + 결과`가 드러나게 쓴다. 다른 화면에 이미 있는 규칙은 다시 쓰지 않고 ID만 참조한다.

| 규칙 ID | 대상 | 조건 | 규칙 | 결과·예외 | 상태·근거 |
| --- | --- | --- | --- | --- | --- |
| SCR-01-R01 | {입력·상태 전이·저장·삭제·중복·알림 등} | ... | ... | ... | 확정/가정/결정 필요 |

## 7. 콘텐츠 요구사항

| 위치 | 반드시 전달할 내용 | 행동·결과 | 관련 규칙 | 상태 |
| --- | --- | --- | --- | --- |
| {버튼/안내/오류} | {사용자가 알아야 할 정보} | {예측해야 할 다음 행동과 결과} | {SCR-01-R..} | {확정/가정/결정 필요} |

## 8. 가정 및 확인 필요

- [ ] {확정되지 않은 요구사항, 규칙, 데이터 계약} — 영향: {요소·상태 ID}
```

## 작성 원칙

- 요소 이름만 나열하지 말고, **누가 어떤 조건에서 무엇을 하고 어떤 결과가 생기는지**를 쓴다.
- 중요도는 화면 목적을 기준으로 판단한다. `핵심`은 없으면 화면 목적을 이룰 수 없는 요소, `보조`는 판단이나 행동을 돕는 요소, `부가`는 없어도 목적을 이룰 수 있는 요소다. 배치나 크기가 아니라 제품상의 중요도이며, 디자이너가 이 값을 근거로 시각 위계를 정한다.
- 정상 흐름과 별개로 로딩, 빈 상태, 입력 오류, 요청 실패, 권한 없음, 긴 콘텐츠를 검토한다. 화면 성격상 해당하지 않으면 이유를 명시한다.
- 목록, 긴 텍스트, 이미지처럼 양이 달라지는 데이터는 보통 양과 최대 양, 초과 시 규칙을 적는다. 입력값 길이·형식은 화면 규칙에 적는다. 근거 없는 수치는 만들지 않고 `결정 필요`로 둔다.
- 버튼의 비활성 조건, 중복 제출 방지, 저장 성공·실패 뒤 데이터 보존 여부를 명확히 한다.
- 접근성에 영향을 주는 레이블, 키보드 조작, 포커스 이동, 오류 전달 방식이 있으면 명시한다.
- 화면 전환은 목적지뿐 아니라 조건도 적는다. 예: `저장 성공 시 상세 화면으로 이동`.
- 법무·보안·결제처럼 위험이 큰 규칙은 단정하지 않고 전문가 확인 필요로 둔다.
- API·데이터 구조·권한이 확정되지 않았다면 임의의 값이나 규칙을 만들지 않는다. 필요한 결정으로 기록한다.
- 버튼 역할을 구분하기 위한 작업용 레이블은 사용할 수 있지만 최종 노출 문구로 확정하지 않는다. UX Writer가 콘텐츠 요구사항과 화면 규칙을 바탕으로 `COPY-*`를 작성한다.

## 완료 전 점검

- 화면 목적과 핵심 사용자 행동이 한 문장으로 설명되는가?
- 각 입력·버튼·목록에 초기 상태와 동작 결과가 있는가?
- 핵심 행동이 하나로 정해져 있고, 모든 요소에 중요도가 있는가?
- 양이 달라지는 데이터에 보통·최대 기준과 초과 시 규칙이 있거나 `결정 필요`로 남아 있는가?
- 성공, 취소/뒤로가기, 오류 흐름이 모두 있는가?
- 입력·상태·삭제처럼 동작을 좌우하는 규칙이 화면 규칙에 있고, 미결정 규칙이 구분되는가?
- 요소와 상태가 관련 흐름·규칙 식별자로 추적되는가?
- 화면 ID와 진입 경로가 IA와 일치하는가?
- 개발자가 추가 해석 없이 구현할 수 있고, QA가 결과를 검증할 수 있는가?
