# 서비스 기획 오케스트레이터

서비스 기획 산출물을 상위 의도부터 구현·측정 기준까지 순차적으로 연결한다. 사용자가 필요한 단계만 요청하면 해당 범위만 실행하되, 앞 단계 정보가 부족한 부분은 가정과 결정 필요로 표시한다.

## 실행 모드

`product-manager`가 PM과 PO의 제품 책임을 통합해 전용 스킬을 순서대로 사용한다. 기획 문서는 순차 의존성이 강하므로 같은 작성 컨텍스트를 유지한다. 전체 초안 작성 후 `spec-reviewer` 한 명을 독립 검토 역할로 실행할 수 있다. 검토자는 작성 문서를 수정하지 않고 보고서만 반환한다.

## 구성

| 단계 | 스킬·에이전트 | 일반 명칭 | 입력 | 기본 출력 |
| --- | --- | --- | --- | --- |
| 0 | 공통 컨텍스트 | - | 사용자 자료 | `planning/00-service-context.md` |
| 1 | `product-brief` | 서비스 기획서 | 아이디어·문제 | `planning/01-product-brief.md` |
| 1a | `brief-enrichment` (선택) | 브리프 보강 제안 | 브리프·아이디어 | `planning/01a-brief-enrichment.md` |
| 2 | `information-architecture` | IA·사이트맵 | 브리프 | `planning/02-information-architecture.md` |
| 3 | `user-flow` | 유저 플로우 | 브리프·IA | `planning/03-user-flow.md` |
| 4 | `policy-spec` | 정책서 | 브리프·IA·흐름 | `planning/04-policy-spec.md` |
| 5 | `screen-spec` | 화면 요구사항 정의서 | IA·흐름·정책 | `planning/05-screen-specs/{screen-id}.md` |

```text
   │  └─ (선택) 인터뷰 → 가정(AS-*) 판정을 제안으로 받아 01에 반영
   ▼
┌▶ 02 IA ─ 화면 ID(SCR) 부여
│  │
│  ▼
└─ 03 유저 플로우 ─ IA에 없는 화면은 '신규' 표시 후 02에 추가
   │
   ▼
   04 정책서 ─ 권한 매트릭스와 IA 접근 제어 일치
   │
   ▼
   05 화면 요구사항 정의서 ─ 요소 동작과 상태
   │
   ▼
   06 인수 조건 ─ Given / When / Then
   │
   ▼
   07 트래킹 플랜 ─ 지표와 이벤트
   │
   ▼
   08 기획 검토
   │  ├─ 근거가 명확한 오기 · 식별자 누락 → 1회 수정
   │  └─ 범위 · 정책 선택 필요 → 결정 질문으로 남김
   ▼
   완료 보고 → 요청 시 디자인 인계
```

IA는 브리프의 MVP 기능과 공통 점검에서 포함된 페이지로 서비스 전체 화면 구조와 화면 ID를 먼저 정하므로 흐름 앞에 둔다. 흐름은 IA의 화면 ID를 사용하고, 흐름을 작성하다 IA에 없는 화면이 필요해지면 IA를 갱신한다. `screen-spec`은 화면의 정보·동작·상태 요구사항을 다루며, 와이어프레임과 배치는 디자인 단계의 `product-ui-design`이 맡는다.

사용자가 출력 루트를 지정하면 표의 `planning/` 앞에 그 경로를 붙인다. 예를 들어 출력 루트가 `experiments/landing`이면 산출물은 `experiments/landing/planning/`에 둔다. 출력 루트가 없을 때만 프로젝트 루트의 `planning/`을 기본값으로 사용한다. 실험 또는 새 서비스의 산출물은 기존 결과를 덮어쓰지 않는다.

이전 번호 체계(IA 없이 `02-user-flow.md`, `03-policy-spec.md`로 이어지는 구성)로 만든 산출물이 이미 있으면 파일명을 바꾸지 않고 기존 경로를 유지한다. 그 폴더에 IA를 추가할 때는 번호 없이 `information-architecture.md`로 둔다.

## Phase 0: 컨텍스트 확인

1. `../../../references/planning-principles.md`, `../../../references/web-service-checklist.md`, `../../../references/service-context.md`, `../../../references/glossary.md`를 읽는다.
2. 사용자 자료와 선택된 출력 루트의 기존 `planning/` 산출물을 확인한다.
3. 실행 유형을 결정한다.
   - 기존 산출물 없음: 초기 실행
   - 특정 문서 수정 요청: 해당 문서와 영향받는 하위 문서만 재실행
   - 새로운 서비스 또는 별도 기능: 기존 결과를 덮어쓰지 않고 사용자와 출력 위치를 구분
4. 확정된 결정은 사용자 요청 없이 변경하지 않는다.

## Phase 1: 범위 설정

사용자 요청에서 다음을 정리한다.

- 이번에 해결할 문제와 우선 사용자
- 전체 서비스인지 특정 기능인지
- 필요한 산출물과 제외할 산출물
- 공통 점검 목록 중 판정할 영역: 서비스 전체면 모든 영역, 특정 기능이면 관련 영역
- 제공된 근거 자료와 제약

필수 정보가 부족해도 안전한 초안 작성이 가능하면 진행한다. 선택에 따라 핵심 범위가 크게 달라지는 경우만 먼저 질문한다.

## Phase 2: 순차 작성

다음 순서로 해당 `SKILL.md`를 읽고 산출물을 작성한다.

1. `../product-brief/SKILL.md`
2. `../information-architecture/SKILL.md`
3. `../user-flow/SKILL.md`
4. `../policy-spec/SKILL.md`
5. `../screen-spec/SKILL.md`
6. `../acceptance-criteria/SKILL.md`
7. `../tracking-plan/SKILL.md`

각 단계에서:

- 상위 문서의 식별자를 유지한다.
- 새 가정과 결정 필요 항목을 명시한다.
- 상위 문서와 충돌하면 하위 문서에서 임의로 해결하지 않는다.
- 다음 단계가 사용할 입력과 미결정 사항을 짧게 정리한다.

흐름 작성 중 `신규`로 표시한 화면이 생기면 흐름을 마친 뒤 IA의 페이지 목록·접근 제어에 추가하고 `흐름 대조`를 갱신한 다음 정책 단계로 넘어간다.

### 브리프 보강 (선택)

브리프 작성 후 사용자가 보강 아이디어를 원하거나, 문제·사용자·MVP 범위가 얇은데 입력에 채울 근거가 없으면 IA 단계 전에 `../brief-enrichment/SKILL.md`로 보강 제안을 만들 수 있다.

- 제안은 `planning/01a-brief-enrichment.md`에 저장하고 브리프에 자동으로 넣지 않는다.
- 사용자가 채택한 제안만 브리프 변경으로 반영하고, 아래 부분 재실행 표의 `제품 브리프` 행에 따라 하위 문서를 확인한다.
- 사용자 판단 없이 후속 단계를 진행하면 완료 보고의 `결정 필요`에 대기 중인 우선순위 `높음` 제안을 적는다.

### 리서치로 검증 (선택)

- 기획서의 `AS-*` 중 우선순위가 높은데 근거가 없는 가정이 있으면 `user-interview` 스킬(`skills/research/user-interview/SKILL.md`)로 인터뷰를 제안할 수 있다.
- 흐름과 화면이 나온 뒤 설계가 통하는지 확인하려면 `usability-test` 스킬(`skills/research/usability-test/SKILL.md`)을 제안할 수 있다.
- 인터뷰와 테스트는 사람이 진행한다. 기록이 없으면 준비 산출물까지만 만들고 가정 상태를 바꾸지 않는다.
- 리서치의 반영 제안(`REC-*`)은 사용자가 채택한 것만 반영하고, 아래 부분 재실행 표에서 해당 문서 행에 따라 하위 문서를 확인한다.

## Phase 3: 독립 검토

전체 또는 2개 이상의 연관 문서를 만들었으면 `../../../agents/spec-reviewer.md`의 역할과 기준으로 독립 검토한다.

- 검토 입력에는 실제 산출물 경로만 전달한다.
- 작성 과정의 의도나 기대 답안을 검토자에게 주입하지 않는다.
- 검토 결과를 `planning/08-spec-review.md`에 저장한다.
- 검토자가 정책을 새로 결정하거나 원문을 직접 수정하게 하지 않는다.

## Phase 4: 결과 반영

1. 근거가 명확한 문서 간 오기·식별자 누락은 1회 수정하고 다시 확인한다.
2. 제품 범위나 정책 선택이 필요한 Blocker/Major는 자동 수정하지 않고 결정 질문으로 남긴다.
3. 최종 보고에서 완료 문서, 미완료 문서, 가정, 결정 필요, 검토 결과를 구분한다.

## 디자인 인계

제품 디자인 요청이 이어지면 `../../../references/product-design-handoff.md`에 따라 우선 사용자, 문제, 목표, MVP 범위, 정보 구조, 흐름, 정책, 화면 요구사항, AC와 용어를 전달한다. 디자인 시스템이나 시각 방향은 이 단계에서 임의 확정하지 않는다.

## 부분 재실행

상위 문서가 바뀌면 다음 영향 범위를 확인한다.

| 변경 문서 | 반드시 다시 확인할 문서 |
| --- | --- |
| 제품 브리프 | IA, 흐름, 정책, 화면, AC, 트래킹 |
| 정보 구조(IA) | 흐름의 화면 ID, 정책의 권한, 화면 진입·접근 조건, 트래킹 |
| 사용자 흐름 | IA(신규 화면), 정책, 화면, AC, 트래킹 |
| 정책 | IA 접근 제어, 화면, AC, 트래킹 |
| 화면 정의서 | AC, 트래킹 |
| 인수 조건 | 관련 화면·정책, 트래킹 |
| 트래킹 플랜 | 목표와 실제 흐름 연결 |

영향 확인과 실제 재작성은 구분한다. 내용이 여전히 유효하면 변경하지 않는다.

## 에러 처리

- 참조 문서가 없으면 누락을 알리고 사용자 입력만으로 가능한 범위를 진행한다.
- 특정 단계가 작성 불가능하면 이유와 필요한 결정을 남기고, 그 결과 없이 진행 가능한 후속 단계만 수행한다.
- 문서가 충돌하면 양쪽 근거를 보존하고 사용자 결정이 필요한 항목으로 올린다.
- 독립 검토를 실행할 수 없는 환경에서는 동일 기준으로 자체 점검하되 독립 검토를 완료했다고 표현하지 않는다.

## 테스트 시나리오

### 정상 흐름

사용자가 대상 사용자, 문제, 핵심 기능이 있는 서비스 아이디어를 제공하면 브리프부터 트래킹까지 연결하고, 검토 보고서에서 각 화면과 IA·정책·AC·이벤트의 추적성을 확인한다.

### 정보 부족 흐름

사용자가 `동네 사람끼리 물건을 빌리는 서비스`만 제공하면 사실처럼 시장 정보를 만들지 않는다. 핵심 사용자와 거래·분쟁 정책을 가정 또는 결정 필요로 표시하고, 정책이 확정되지 않은 AC와 이벤트의 한계를 명시한다. 공통 점검의 결제·신고 영역도 판정 근거가 없으면 `결정 필요`로 남긴다.

### 흐름에서 화면이 추가되는 흐름

IA에 없던 `비밀번호 재설정` 화면이 가입 흐름 작성 중 필요해지면 흐름에 `신규`로 표시하고, 흐름을 마친 뒤 IA의 페이지 목록·접근 제어·흐름 대조를 갱신한다. 흐름에서 새 화면 ID를 확정하지 않고 IA의 번호 규칙을 따른다.

### 부분 수정 흐름

사용자가 기존 정책에서 `비회원 조회 허용`만 변경하면 정책 문서를 수정하고 IA 접근 제어, 화면 접근 조건, 관련 AC, 조회 이벤트 세그먼트의 영향만 확인한다. 제품 브리프의 유효한 내용은 다시 작성하지 않는다.
