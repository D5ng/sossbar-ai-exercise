# 사용성 테스트

사용자가 실제로 과제를 해낼 수 있는지, 어디서 막히는지 관찰해 흐름·화면·문구의 문제를 찾는다. 인터뷰가 어떤 문제가 있는지를 알아낸다면, 사용성 테스트는 이 설계가 통하는지를 확인한다.

```text
준비 모드 ─ 테스트 전
│  대상 화면 · 과제 · 성공 기준 · 진행 스크립트
▼
실제 테스트 ─ 사람이 진행하고 기록을 제공한다
│
▼
분석 모드 ─ 테스트 후
   과제 결과 · 사용성 문제 · 심각도 · 반영 위치
```

## 절대 규칙

- 참가자 행동, 성공 여부, 발언, 소요 시간을 만들어내지 않는다. 분석은 사용자가 제공한 기록에만 근거한다.
- 기록 없이 화면을 점검해 달라는 요청은 사용성 테스트가 아니다. 전문가 점검은 `design-review`나 `accessibility-review`로 안내하고, 그 결과를 사용성 테스트 결과로 표시하지 않는다.
- 해결 디자인을 직접 확정하지 않는다. 문제, 반영 위치, 개선 방향까지만 제시하고 실제 수정은 해당 문서의 담당 스킬이 한다.
- 참가자는 `PT-*`로 익명 처리하고 화면 녹화·녹음 동의 방식은 사용자가 정한다.

## 참조

- `../../../references/planning-principles.md`
- `../../../references/product-design-handoff.md`
- `../../../references/glossary.md`
- 관련 유저 플로우(`F-*`), 화면 요구사항 정의서(`SCR-*`), UI 명세(`UI-*`)와 문구(`COPY-*`)가 있으면 먼저 읽는다.
- 테스트할 프로토타입이나 화면의 위치와 버전

## 준비 모드

### 작성 절차

1. 이 테스트로 내릴 결정과 범위를 정하고 대상 흐름·화면 ID를 연결한다.
2. 과제(`T-*`)를 만든다.
   - 사용자의 목표를 상황으로 제시한다. 예: `친구 생일 선물로 3만 원 이하 상품을 골라 장바구니에 담아 보세요`.
   - 화면의 버튼·메뉴 이름을 과제 문장에 쓰지 않는다. 답을 알려 주는 셈이 되기 때문이다.
   - 과제마다 관찰 가능한 성공 기준을 정한다. 관련 `F-*`, `SCR-*`가 있으면 연결한다.
3. 앞 과제가 뒤 과제의 힌트가 되지 않도록 순서를 정한다.
4. 진행 스크립트를 도입, 생각 말하기 안내, 과제, 과제별 후속 질문, 마무리 순서로 만든다.
5. 진행자 규칙을 적는다. 막혀도 바로 돕지 않고, 참가자가 물으면 `어떻게 하실 것 같으세요?`로 되묻고, 도움을 줬다면 기록한다.
6. 참가자 조건과 수, 대면·원격 방식은 사용자 결정으로 남긴다.
7. 과제 결과, 막힌 지점, 오류, 발언을 나눠 적는 기록 양식을 준다.

### 준비 모드 출력

기본 저장 위치는 `research/usability/{study-slug}/01-plan.md`다.

````markdown
# {대상} 사용성 테스트 계획

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 스터디 ID | RS-02 |
| 이 테스트로 내릴 결정 | ... |
| 대상 흐름·화면 | F-01, SCR-01 ~ SCR-04 |
| 테스트 자료 | {프로토타입 위치와 버전} |
| 방식 | 대면/원격 — 결정 필요 |

## 2. 과제

| 과제 ID | 시나리오(참가자에게 읽어 줄 문장) | 성공 기준 | 관련 흐름·화면·AC |
| --- | --- | --- | --- |
| T-01 | ... | {관찰 가능한 완료 상태} | F-01, SCR-02 |

## 3. 과제 경로

```text
T-01 {과제 요약} ─ 시작: SCR-01
│
▼
SCR-02 {기대 행동}
│  └─ 예상 막힘: {지점} → 관찰 포인트
▼
SCR-03 성공: {완료 상태}
```

## 4. 진행 스크립트

1. 도입: 평가 대상은 참가자가 아니라 화면이라는 점, 생각을 소리 내어 말해 달라는 요청, 녹화 동의
2. 과제: 시나리오 문장만 읽고 추가로 설명하지 않는다
3. 과제별 후속 질문: `어려웠던 부분이 있었나요?`, `기대한 것과 달랐던 점은요?`
4. 마무리: 전체 소감, 감사 인사

## 5. 기록 양식

| 참가자 | 과제 | 결과 | 막힌 지점·화면 | 오류·우회 행동 | 발언 |
| --- | --- | --- | --- | --- | --- |
| PT-01 | T-01 | 성공/도움 받아 성공/실패/포기 | SCR-02 | ... | "..." |

## 6. 진행 전 확인

- [ ] 참가자 조건·수·보상
- [ ] 녹화·녹음 동의 — 필요하면 전문가 확인
- [ ] 테스트 자료 버전 고정
- [ ] 진행자와 기록자 분리 여부
````

## 분석 모드

### 분석 절차

1. 참가자를 `PT-*`로 익명 처리한다.
2. 과제별 결과를 성공, 도움 받아 성공, 실패, 포기로 기록에서 센다. 소요 시간은 기록에 측정값이 있을 때만 쓴다.
3. 막힌 지점, 오류, 우회 행동을 사용성 문제(`UT-*`)로 묶는다. 같은 원인은 하나로 묶고 발생한 참가자를 모두 적는다.
4. 문제마다 아래 기준으로 심각도를 판정한다.
5. 원인에 따라 반영 위치를 정한다.
6. 개선 방향을 적되 해결 디자인은 확정하지 않고 반영 제안(`REC-*`)으로 남긴다.
7. 잘 된 점도 기록한다. 바꾸지 말아야 할 부분을 알려 준다.

### 심각도

| 등급 | 기준 |
| --- | --- |
| 치명 | 과제를 끝낼 수 없게 하거나, 데이터 손실·잘못된 결제처럼 되돌리기 어려운 결과를 낸다 |
| 높음 | 과제는 끝내지만 큰 지연, 반복 오류, 도움 요청을 일으킨다 |
| 중간 | 잠시 멈추거나 헤매지만 스스로 회복한다 |
| 낮음 | 과제 수행에 영향이 없는 불편이나 어색함이다 |

발생 인원은 심각도와 따로 적는다. 한 명에게만 생긴 문제라도 치명일 수 있다.

### 반영 위치

```text
UT-* 원인
├─ 규칙이 없거나 모호함 → 화면 규칙 SCR-*-R*
├─ 경로나 단계가 맞지 않음 → 유저 플로우 F-*
├─ 필요한 정보나 상태가 빠짐 → 화면 요구사항 정의서 SCR-*
├─ 배치 · 위계 · 상호작용 → UI 명세 UI-*
├─ 문구를 이해하지 못함 → 문구 COPY-*
└─ 공통 컴포넌트의 한계 → 시스템 공백 GAP-*
```

IA·유저 플로우·화면 요구사항 정의서가 원인이면 `service-planning`, UI·문구·컴포넌트가 원인이면 `product-design`의 부분 재실행으로 반영한다.

### 분석 모드 출력

기본 저장 위치는 `research/usability/{study-slug}/03-findings.md`다. 사용자가 제공한 원본 기록은 `02-notes/`에 두며 이 스킬이 작성하지 않는다.

````markdown
# {대상} 사용성 테스트 결과

## 1. 요약

| 항목 | 내용 |
| --- | --- |
| 스터디 ID | RS-02 |
| 참가자 | {n}명, 기록 기준 |
| 테스트 자료 | {버전} |
| 치명·높음 문제 | UT-01, UT-03 |

## 2. 과제 결과

| 과제 | 성공 | 도움 받아 성공 | 실패·포기 | 주요 막힌 지점 |
| --- | --- | --- | --- | --- |
| T-01 | {n} | {n} | {n} | SCR-02 |

```text
T-01 {과제 요약}
SCR-01 ─ {n}명 시작
│
▼
SCR-02 ─ {n}명 통과
│  └─ {n}명 막힘 → UT-01
▼
SCR-03 ─ {n}명 성공
```

## 3. 사용성 문제

| 문제 ID | 문제 | 발생 위치 | 심각도 | 발생 참가자 | 근거 | 반영 위치 |
| --- | --- | --- | --- | --- | --- | --- |
| UT-01 | ... | T-01 · SCR-02 | 치명/높음/중간/낮음 | PT-01·03 ({n}/{전체}명) | "{기록 원문}" 또는 관찰 요약 | UI-02 / SCR-02-R01 / COPY-05 |

## 4. 잘 된 점

- {유지해야 할 설계와 근거}

## 5. 반영 제안

| 제안 ID | 문제 | 대상 문서·ID | 개선 방향 | 판단 |
| --- | --- | --- | --- | --- |
| REC-01 | UT-01 | UI-02 | ... | 대기 |

## 6. 이번 테스트로 확인하지 못한 것

- {범위 밖 화면, 기록 부족 등}
````

`판단`은 `대기`, `채택`, `보류`, `거절`, `반영됨 → {ID}` 중 하나다.

## 완료 기준

- 준비 모드: 과제 문장에 화면의 버튼·메뉴 이름이 없고, 모든 과제에 관찰 가능한 성공 기준이 있다.
- 분석 모드: 과제 결과와 문제별 인원이 기록에서 센 값이다.
- 모든 사용성 문제에 심각도, 근거, 반영 위치가 있다.
- 해결 디자인을 확정하지 않고 반영 제안으로 남겼다.
- 기록에 없는 행동, 발언, 시간을 쓰지 않았다.
- 산출물에 개인 식별 정보가 없다.

## 테스트 시나리오

### 계획 요청

가입 흐름 F-01과 SCR-01~04가 있으면 `T-*` 과제를 만들고, 과제 문장에 버튼 이름 대신 목표 상황을 쓴다. 참가자 수와 방식은 결정 필요로 남긴다.

### 기록 없는 점검 요청

`이 화면 사용성 괜찮은지 봐줘`라는 요청은 사용성 테스트 결과로 만들지 않고 `design-review` 같은 전문가 점검을 안내한다.

### 분석 요청

참가자 다섯 명의 기록에서 세 명이 SCR-02에서 막혔다면 UT-01로 묶고 인원을 3/5로 적는다. 원인이 문구라면 반영 위치를 `COPY-*`로 정하고 반영 제안을 남긴다.
