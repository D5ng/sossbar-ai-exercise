# 사용자 인터뷰

사용자가 실제로 겪는 상황, 지금 쓰는 대안, 행동의 이유를 알아내 기획의 가정을 지지하거나 반박한다. 이 스킬은 인터뷰 전의 준비 모드와 인터뷰 후의 분석 모드로 동작한다.

```text
준비 모드 ─ 인터뷰 전
│  리서치 질문 · 참가자 조건 · 인터뷰 가이드
▼
실제 인터뷰 ─ 사람이 진행하고 기록을 제공한다
│
▼
분석 모드 ─ 인터뷰 후
   인사이트 · 가정 판정 · 반영 제안
```

## 절대 규칙

- 참가자 응답, 인용, 인원수, 결과를 만들어내지 않는다. 분석은 사용자가 제공한 기록에만 근거한다.
- 기록 없이 예상 반응이나 가상 사용자 응답을 요청받으면 리서치 결과가 아니라 `가정`으로만 표시하고, 인사이트나 가정 판정으로 쓰지 않는다.
- 기획서와 서비스 컨텍스트를 직접 수정하지 않는다. 반영은 제안(`REC-*`)으로 남기고 사용자가 채택한 것만 `service-planning` 부분 재실행으로 반영한다.
- 참가자는 `PT-*`로 익명 처리한다. 이름, 연락처, 회사명처럼 개인을 알아볼 수 있는 정보를 산출물에 옮기지 않는다.
- 녹음·녹화, 보상, 개인정보 수집 동의는 사용자가 정한다. 필요한 항목을 체크리스트로 제시하고 법적 요건은 전문가 확인 필요로 표시한다.

## 참조

- `../../../references/planning-principles.md`
- `../../../references/service-context.md`
- `../../../references/glossary.md`
- 기획서가 있으면 문제(`P-*`), 대상 사용자, 주요 가정(`AS-*`)과 성공 신호(`M-*`)를 먼저 읽는다.
- 이전 인터뷰 산출물이 있으면 함께 읽는다.

## 준비 모드

### 작성 절차

1. 이 인터뷰로 내릴 결정과 리서치 질문(`RQ-*`)을 정한다. 검증할 `AS-*`와 알아볼 `P-*`를 연결한다.
2. 참가자 조건을 정한다. 포함·제외 조건은 인구 통계보다 행동과 상황으로 쓴다. 예: `최근 3개월 안에 중고 물품을 직접 거래해 본 사람`.
3. 참가자 수, 모집 경로, 일정, 보상은 사용자 결정으로 남긴다. 정성 인터뷰는 통계적 대표성을 주장하지 않는다.
4. 인터뷰 가이드를 도입, 맥락, 최근 경험, 현재 대안, 마무리 순서로 만든다.
5. 질문을 점검한다.
   - 미래를 가정하는 질문(`이 기능이 있으면 쓰시겠어요?`) 대신 지난 행동을 묻는다(`마지막으로 ○○했을 때 어떻게 하셨어요?`).
   - 답을 유도하는 질문, 한 번에 두 가지를 묻는 질문, 해결책을 소개하는 질문을 뺀다.
   - 핵심 질문마다 후속 질문(`그때 왜 그렇게 하셨어요?`, `그다음엔요?`)을 준비한다.
6. 관찰(한 일), 발언(한 말), 해석(기록자 생각)을 나눠 적는 기록 양식을 준다.

### 준비 모드 출력

기본 저장 위치는 `research/interviews/{study-slug}/01-plan.md`다.

````markdown
# {주제} 인터뷰 계획

## 1. 개요

| 항목 | 내용 |
| --- | --- |
| 스터디 ID | RS-01 |
| 이 인터뷰로 내릴 결정 | ... |
| 검증할 가정 | AS-01, AS-02 |
| 관련 문제·목표 | P-01, G-01 |
| 상태 | 계획 중 / 진행 중 / 분석 완료 |

## 2. 리서치 질문

| ID | 알고 싶은 것 | 연결 | 이 답으로 달라지는 결정 |
| --- | --- | --- | --- |
| RQ-01 | ... | AS-01 | ... |

## 3. 참가자 조건

| 구분 | 조건 | 이유 |
| --- | --- | --- |
| 포함 | {행동·상황 기준} | ... |
| 제외 | ... | ... |

- 참가자 수·모집 경로·보상: 결정 필요
- 선별 질문: {포함 조건을 확인하는 질문}

## 4. 인터뷰 가이드

```text
도입 ─ 목적 · 녹음 동의 · 정답이 없다는 안내
│
▼
맥락 ─ 평소 {상황}이 어떻게 생기는지
│
▼
최근 경험 ─ 마지막으로 {행동}했을 때 처음부터 끝까지
│  └─ 후속: 그때 왜 · 그다음엔 · 가장 번거로웠던 점
▼
현재 대안 ─ 지금 무엇으로 해결하는지 · 좋은 점과 불편
│
▼
마무리 ─ 빠진 이야기 · 감사 인사
```

| 순서 | 질문 | 확인할 RQ | 후속 질문 |
| --- | --- | --- | --- |
| 1 | ... | RQ-01 | ... |

## 5. 기록 양식

| 시점 | 관찰(한 일) | 발언(한 말) | 해석(기록자) |
| --- | --- | --- | --- |
| ... | ... | ... | ... |

## 6. 진행 전 확인

- [ ] 녹음·녹화 동의 방식
- [ ] 개인정보 수집·보관·파기 방식 — 전문가 확인 필요
- [ ] 보상 방식
- [ ] 진행자와 기록자 분리 여부
````

## 분석 모드

### 입력

- 사용자가 제공한 인터뷰 기록, 녹취록 또는 메모. 참가자별로 구분돼 있어야 한다.
- 준비 모드의 계획 문서. 없으면 기록에서 리서치 질문을 거꾸로 정리하고 `계획 없이 진행`으로 표시한다.

### 분석 절차

1. 참가자마다 `PT-*`를 붙이고 개인 식별 정보를 지운다.
2. 기록에서 관찰과 발언을 한 줄 단위로 뽑는다. 원문 인용은 기록에 있는 문장만 쓰고, 요약했으면 `요약`이라고 표시한다.
3. 비슷한 관찰을 묶어 패턴을 찾는다. 몇 명에게서 나왔는지는 실제 기록에서 센다.
4. 패턴에서 인사이트(`INS-*`)를 쓴다. 인사이트는 `{누가} {어떤 상황에서} {무엇 때문에} {어떻게 행동한다}` 형태로, 관찰보다 한 단계 해석한 문장이다.
5. 가정(`AS-*`)마다 지지, 반박, 불명확 중 하나로 판정한다. 근거 참가자와 반대 사례를 함께 적는다.
6. 기획 반영 제안(`REC-*`)을 만든다. 어느 문서의 어느 ID가 바뀌는지 적고, 채택은 사용자가 정한다.
7. 기록으로 답하지 못한 리서치 질문과 다음 리서치 제안을 남긴다.

### 분석 모드 출력

기본 저장 위치는 `research/interviews/{study-slug}/03-synthesis.md`다. 사용자가 제공한 원본 기록은 `02-notes/`에 두며 이 스킬이 작성하지 않는다.

````markdown
# {주제} 인터뷰 분석

## 1. 요약

| 항목 | 내용 |
| --- | --- |
| 스터디 ID | RS-01 |
| 참가자 | {n}명 (PT-01 ~ PT-{nn}), 기록 기준 |
| 핵심 인사이트 | INS-01, INS-02 |
| 가정 판정 | AS-01 반박, AS-02 지지 |

## 2. 참가자

| ID | 충족한 조건 | 특징(식별 정보 제외) |
| --- | --- | --- |
| PT-01 | ... | ... |

## 3. 인사이트

### INS-01 {인사이트 문장}

- 근거: PT-01, PT-03, PT-04 ({n}/{전체}명)
- 대표 발언: "{기록에 있는 원문}" — PT-03
- 반대 사례: {없음 또는 해당 참가자와 행동}
- 연결: RQ-01, AS-01, P-01

```text
INS-01
├─ PT-01 {관찰 요약}
├─ PT-03 {관찰 요약}
├─ PT-04 {관찰 요약}
└─ 반대 사례 PT-02 {관찰 요약}
```

## 4. 가정 판정

| 가정 | 판정 | 근거 | 반대 사례 | 다음 행동 |
| --- | --- | --- | --- | --- |
| AS-01 | 지지/반박/불명확 | INS-01, PT-01·03 | ... | 유지/수정 제안/추가 검증 |

## 5. 반영 제안

| 제안 ID | 대상 문서·ID | 바꿀 내용 | 근거 | 판단 |
| --- | --- | --- | --- | --- |
| REC-01 | 기획서 P-01 | ... | INS-01 | 대기 |

## 6. 답하지 못한 질문과 다음 리서치

- RQ-02: {기록에 근거가 없음} — 제안: {방법}
````

`판단`은 `대기`, `채택`, `보류`, `거절`, `반영됨 → {ID}` 중 하나다.

## 완료 기준

- 준비 모드: 모든 인터뷰 질문이 `RQ-*`와 연결되고, 미래를 가정하는 질문과 유도 질문이 없다.
- 분석 모드: 모든 인사이트에 실제 기록의 근거 참가자와 인원이 있다.
- 기록에 없는 인용, 수치, 결과가 없다.
- 가정마다 판정과 근거가 있고 반대 사례를 숨기지 않는다.
- 기획서를 직접 고치지 않고 반영 제안으로 남겼다.
- 산출물에 개인 식별 정보가 없다.

## 테스트 시나리오

### 계획 요청

기획서에 `AS-01 사용자는 신뢰 문제 때문에 물건 빌리기를 망설인다`가 있고 인터뷰 계획을 요청하면, AS-01을 확인할 `RQ-*`와 지난 행동 중심의 질문을 만들고 참가자 수와 보상은 결정 필요로 남긴다.

### 기록 없는 분석 요청

기록 없이 `사용자 반응을 예상해서 정리해줘`라고 하면 인사이트와 가정 판정을 만들지 않는다. 필요하면 `가정` 목록으로만 제시하고 실제 인터뷰가 필요하다고 알린다.

### 분석 요청

참가자 다섯 명의 메모가 주어지면 PT-01~05로 익명화하고, 인사이트마다 근거 참가자를 기록에서 세며, AS 판정과 반영 제안을 만든다. 기획서는 수정하지 않는다.
